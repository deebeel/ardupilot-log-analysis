# Стенд SITL + сервіс аналізу якості пілотування

Тестове завдання RND-254. Дві ізольовані мережі, з'єднані WireGuard-тунелем:

- **Мережа A (SITL)** — окрема Ubuntu-машина (VM або bare-metal): SITL ArduPlane, MAVProxy
  (GCS + 2D-візуалізатор + авіагоризонт), клавіатурний адаптер замість джойстика.
- **Мережа B (GCS/VPS)** — окремий Ubuntu VPS: приймач логів (`parser`) і WEB-звіт (`web`),
  обидва в Docker, за Caddy (звичайний HTTP — без сертифікатів, див. нижче).

Телеметрія й логи ходять лише через WireGuard — іншого маршруту між мережами немає.

Це канонічний README — покриває лише Ubuntu (те саме середовище, що в тікеті). Для
розробки `parser`/`web` на macOS — `README.mac.md` (рев'юєру не потрібен).

## Структура репозиторію

```
local/                        # Мережа A (SITL-хост)
├── provision.sh               # одноразовий провіжн SITL-хоста (sudo)
├── setup-wireguard.sh          # клієнтський бік тунелю: авто (SSH на VPS) або ручний
├── run-sitl.sh                  # повторюваний запуск SITL+MAVProxy (без sudo)
├── push-logs.sh                 # автоматична доставка логів на VPS (фон, запускається run-sitl.sh)
└── keyboard_adapter/              # MAVProxy-модуль: клавіатура -> MANUAL_CONTROL
vps/                        # Мережа B (VPS)
├── provision.sh                # одноразовий провіжн VPS: Docker, ufw, збірка образів
│                               # і `docker compose up -d` — все в одному прогоні
├── setup-wireguard.sh           # серверний бік тунелю (ручний або викликається з local/ по SSH)
├── services/
│   ├── parser/                   # приймач + аналізатор логів (Python, pymavlink)
│   └── web/                       # звіт (Astro/TS)
└── compose/                      # docker-compose.yml, Caddyfile, .env.example
docs/
├── implementation-plan.md       # детальний план реалізації (сервіси, компроміси)
├── host-prerequisites.md        # чернетка, з якої зібрано розділ SITL нижче
└── scoring-algorithm.md         # алгоритм вердикту (if/else за порогами)
```

`local/` — усе, що працює на SITL-хості (Мережа A); `vps/`, включно з самими
сервісами (`vps/services/`), — усе, що працює на VPS (Мережа B). Назва теки
відповідає мережі, а не типу артефакту (скрипт/сервіс) — `parser`/`web` ніде, крім VPS,
не запускаються, тож логічно є частиною `vps/`, а не окремою верхньорівневою текою.

`local/provision.sh` і `vps/provision.sh` — однакова назва файлу навмисно: та сама
роль (одноразовий, sudo, ідемпотентний провіжн), той самий патерн, різні хости. Обидва
запускаються з клона репозиторія на своєму хості — жодних кроків з робочої машини.
WireGuard між ними піднімає окремий `local/setup-wireguard.sh` — не частина жодного
з двох провіжнів (див. крок 1.2 нижче).

## Що дається замовником

- VPS (Ubuntu) з SSH-доступом. DNS-ім'я та SSL-сертифікат — коли будуть надані, стенд
  зараз працює без них (плейн HTTP, див. крок 2).
- Шаблони "добрих"/"поганих" патернів керування (для порогів вердикту).
- Програма польоту (льотні вправи) — до отримання: `docs/scoring-algorithm.md`/демо-політ.

## Крок 1. Мережа A — SITL-хост

Клонувати репозиторій на чисту Ubuntu VM (або bare-metal):

```bash
sudo apt-get install -y git   # якщо git ще нема
git clone <URL_РЕПОЗИТОРІЮ>
cd <ТЕКА_РЕПОЗИТОРІЮ>
```

### 1.1. Одноразовий провіжн

```bash
./local/provision.sh
```

Один `sudo`-запит. Клонує **офіційний апстрім** ArduPilot (не форк) у гітигнорену
`.sitl/`, виставляє тег `Plane-4.6.3` (перевизначити: `ARDUPILOT_TAG=... ./local/provision.sh`),
запускає ArduPilot-івський `install-prereqs-ubuntu.sh` (ставить MAVProxy/pymavlink у
`~/venv-ardupilot`, компілює wxPython — 20-40+ хв першого разу), додає
`wireguard-tools`/`rsync`/`openssh-client`/`git-lfs`/`inotify-tools` (доставка логів) і
групу `input` (клавіатурний бекенд `evdev`). WireGuard ще НЕ піднімається тут — крок 3.

Якщо групу `input` щойно додано — **релогін** (вийти й зайти знову) перед наступним кроком.

## Крок 2. Мережа B — VPS

Клонувати той самий репозиторій на VPS:

```bash
ssh root@<vps>
apt-get install -y git   # якщо git ще нема
git clone <URL_РЕПОЗИТОРІЮ>
cd <ТЕКА_РЕПОЗИТОРІЮ>
```

### 2.1. Одноразовий провіжн

```bash
./vps/provision.sh
```

Все в одному прогоні: Docker Engine (офіційний apt-репозиторій), `wireguard-tools`,
`ufw` (22/80/51820-udp — без 443, без сертифікатів), теки `/srv/app/data/{inbox,results}`,
і одразу **збірка образів `parser`/`web` та `docker compose up -d`** — усе тут же, на
самому VPS (він уже нативний `amd64`, тож крос-збірка/перенесення образів іншим шляхом
не потрібні). WireGuard ще НЕ піднімається тут — крок 3, з SITL-хоста. Ідемпотентний —
повторний прогін (напр. після `git pull` з новим кодом) сам пересобере й перезапустить
контейнери.

### 2.2. Перевірка

```bash
curl http://localhost/       # з самого VPS — має відповідати HTML звіту
docker compose --project-directory vps/compose -f vps/compose/docker-compose.yml ps
```

Зовнішньо — `http://<ip_або_домен_vps>/`. Без сертифікатів свідомо: SSL/домен від
замовника — окремий крок пізніше (підстановка в `vps/compose/Caddyfile`), не частина
поточного провіжну.

## Крок 3. WireGuard-тунель (обидва боки, з SITL-хоста)

Повертаємось на SITL-хост. SSH-доступ до VPS уже є (клонували туди репозиторій на
кроці 2) — тим самим доступом піднімаємо тунель одним скриптом, без ручного
копіювання публічних ключів між двома терміналами:

```bash
VPS_HOST=root@<vps> ./local/setup-wireguard.sh
```

Генерує WireGuard-ключ клієнта тут (якщо ще нема), по SSH генерує ключ сервера на VPS
(якщо ще нема) і сам пише `wg0.conf` на обох боках — і тут, і на VPS через той самий
SSH. Завершується перевіркою (`ping 10.10.0.1` крізь тунель). `VPS_ENDPOINT` (публічна
адреса VPS для клієнтського `Endpoint`) за замовчуванням береться з `VPS_HOST`; якщо
SSH ходить не туди, куди має слухати WireGuard — перевизначити явно:
`VPS_HOST=root@<vps> VPS_ENDPOINT=<публічний_ip_або_домен>:51820 ./local/setup-wireguard.sh`.

Ідемпотентний — повторний прогін (напр. після переліту SITL-хоста чи зміни VPS)
перезапише конфіги обох боків і перепідніме `wg0`.

**Якщо SSH з SITL-хоста на VPS немає** (інша мережа, фаєрвол, VPS адмінить хтось
інший) — тунель усе одно потрібен (це прямий критерій приймання тікета), просто
обмін публічними ключами стає ручним, без SSH:

```bash
# 1. Тут: друкує публічний ключ клієнта, wg0 ще НЕ піднятий
./local/setup-wireguard.sh

# 2. На VPS (яким завгодно доступом): друкує публічний ключ сервера
CLIENT_WG_PUBKEY=<ключ_з_1> ./vps/setup-wireguard.sh

# 3. Тут: тепер піднімає wg0
SERVER_WG_PUBKEY=<ключ_з_2> VPS_ENDPOINT=<ip_або_домен_vps>:51820 ./local/setup-wireguard.sh
```

## Крок 4. Запуск SITL + MAVProxy + керування

```bash
./local/run-sitl.sh
```

Піднімає SITL ArduPlane, MAVProxy (`--console --map`) з модулями `keyboard_adapter` і
`horizon` (авіагоризонт, окреме wx-вікно), і у фоні `push-logs.sh` (автоматична доставка
логів на VPS через уже піднятий тунель). `.BIN`/`.tlog` — в `.sitl/ArduPlane/logs/`.

Клавіатурне керування (замість джойстика — обґрунтування в `local/keyboard_adapter/README.md`):

| Клавіші | Вісь |
|---|---|
| `W` / `S` | pitch |
| `A` / `D` | roll |
| `Q` / `E` | yaw |
| `Up` / `Down` | throttle (утримується, без spring-return) |

Тротл свідомо на `Up`/`Down`, не `Shift`/`Ctrl`: `evdev` читає клавіші сиро, незалежно
від фокуса вікна — `Shift`/`Ctrl` як модифікатори під час друку команд у `MAV>`-консолі
заодно рухали б тротл.

Керування клавіатурою вмикається **явно**, окремою командою в консолі `MAV>` — недостатньо
просто озброїтись і бути в `FBWA`:

```
mode FBWA
arm throttle
kb on      # клавіатура НЕ керує, доки не введено цю команду
```

`kb off`, вихід із `FBWA` чи `disarm` — будь-яке з цього зупиняє керування. Завершення
сесії: `disarm`, потім `Ctrl+C` (зупиняє SITL, MAVProxy і всі модулі разом).

Якщо автовизначення клавіатури обрало не той `/dev/input/eventN` —
`KEYBOARD_DEVICE=/dev/input/eventN ./local/run-sitl.sh` (`ls /dev/input/by-id/` для пошуку).

## Крок 5. Політ і звіт

1. На SITL-хості: `mode FBWA` → `arm throttle` → `kb on` → пілотувати за програмою польоту
   (льотні вправи від замовника; до отримання — `docs/scoring-algorithm.md`).
2. `disarm`, потім `Ctrl+C` — завершує сесію.
3. Лог (`.BIN`, закритий на дизармі) автоматично потрапляє на VPS через `push-logs.sh`
   (фон, запущений `run-sitl.sh`) — жодної ручної команди після польоту не потрібно.
4. Відкрити `http://<vps>/` — новий політ з'являється у списку (з бейджем вердикту)
   протягом секунди (клієнтський поллінг), звіт по кліку показує графік стіків поверх
   attitude, гістограму амплітуд і зведені метрики з підсумковою оцінкою.
5. Повторити щонайменше 3 рази для здачі — **тією ж програмою польоту** (інакше метрики
   різних польотів непорівнянні).

## Ключові рішення (короткий дайджест — повна історія й компроміси в `CLAUDE.md`)

- **Клавіатура замість джойстика** — погоджено із замовником; spring-return на
  roll/pitch/yaw, щоб клавіатурний ввід не спотворював метрики амплітуди/різкості.
- **keyboard-адаптер — MAVProxy-модуль**, не окремий процес: ідіоматично для MAVProxy
  (так само map/console), без власного UDP-конекту. Компроміс: падіння самого MAVProxy
  тепер тягне за собою й керування (падіння окремого модуля — ні).
  - Клавіатурний бекенд — лише `evdev` (Xorg і Wayland однаково; тротл на `Up`/`Down`, не
    `Shift`/`Ctrl` — не заплутуються з друком команд у консолі).
  - Керування вмикається лише в `FBWA` + armed + явний `kb on` — жодна з двох перших умов
    сама по собі (можна виникнути на землі/під час рулювання) не запускає керування.
- **`horizon`** (штатний MAVProxy-модуль) — доданий для живого фідбека тангажа/крену під
  час пілотування; `speech`/`graph` розглядались і відхилені (зайва вага без вигоди).
- **Розгортання — shell (`local/provision.sh` + `vps/provision.sh`), не Ansible.**
  Один VPS, одноразовий прогін — цінність Ansible (ідемпотентність для флоту хостів) тут
  не окупається. Обидва скрипти запускаються з клона репозиторія на своєму хості.
- **WireGuard — окремі симетричні скрипти (`local/setup-wireguard.sh` +
  `vps/setup-wireguard.sh`), не частина жодного `provision.sh`.** Тунель — прямий
  критерій приймання тікета, тож потрібен незалежно від того, чи є SSH між
  хостами: якщо є (типовий випадок — SITL-хост тим самим SSH клонував репо на VPS
  і запускав `vps/provision.sh`) — `local/setup-wireguard.sh` з `VPS_HOST=...`
  піднімає ОБИДВА боки одним запуском, викликаючи `vps/setup-wireguard.sh`
  віддалено; якщо SSH нема (інша мережа, VPS адмінить хтось інший) — той самий
  `vps/setup-wireguard.sh` запускається вручну на VPS, а публічні ключі
  передаються між скриптами людиною (`SERVER_WG_PUBKEY`/`CLIENT_WG_PUBKEY`).
- **Образи для VPS збираються прямо на самому VPS**, під час `vps/provision.sh` —
  VPS уже нативний `amd64`, окремого кроку "зібрати на робочій машині й перенести" нема.
- **`local/provision.sh` shallow-клонує ArduPilot** (`--depth 1 --branch <тег>`), не
  всю історію апстріму — SITL-збірці історія не потрібна, а репозиторій ArduPilot
  великий (десятки тисяч комітів, багато тегів).
- **Без сертифікатів (поточний стан)** — Caddy лише проксує звичайний HTTP; SSL/домен від
  замовника підставляються окремим кроком пізніше, коли будуть надані.
- **Доставка логів — автоматична** (`local/push-logs.sh`, `inotifywait` на `close_write`),
  не окрема ручна команда після кожного польоту — прямий критерій приймання тікета.
- **Вердикт — if/else за конфігом порогів, без LLM.** Пороги — на клієнті (браузер рахує
  категорію миттєво, сервер віддає лише метрики + дефолтні пороги).
- **`crashed` — окрема категорія, що переважає над good/warning/bad** — `STAT.Crash` сам
  по собі не годиться (не спрацьовує в ручних режимах), тож комбінується з евристикою.

## Що не встигнуто / відомі обмеження

- Пороги вердикту (`vps/services/parser/thresholds.yaml`) — **placeholder** з демо-польоту, не
  реальні good/bad-шаблони замовника (замінюються без зміни коду — лише конфіг).
- Програма польоту — тимчасовий сурогат (`docs/scoring-algorithm.md`), очікує підтвердження
  від замовника.
- DNS-ім'я та SSL-сертифікат від замовника ще не отримані — стенд свідомо працює без
  сертифікатів (плейн HTTP); коли будуть надані, підставляються в `vps/compose/Caddyfile`.
- Живий прогін через справжній WireGuard-тунель між реальною SITL-VM і реальним VPS — до
  моменту здачі ще підлягає повторній перевірці (стенд перевірявся частинами).
