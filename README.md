# Стенд SITL + сервіс аналізу якості пілотування

Тестове завдання RND-254. Дві ізольовані мережі, з'єднані WireGuard-тунелем:

- **Мережа A (SITL)** — окрема Ubuntu-машина (VM або bare-metal): SITL ArduPlane, MAVProxy
  (GCS + 2D-візуалізатор + авіагоризонт), клавіатурний адаптер замість джойстика.
- **Мережа B (GCS/VPS)** — окремий Ubuntu VPS з SSH-доступом і DNS-ім'ям: приймач логів
  (`parser`) і WEB-звіт (`web`), обидва в Docker, за Caddy (HTTP і HTTPS; SSL-сертифікат
  — self-signed за замовчуванням, підмінюється реальним без зміни коду, див. розділ
  «Сертифікат HTTPS» нижче).

Телеметрія й логи ходять лише через WireGuard — іншого маршруту між мережами немає.

Це канонічний README — покриває лише Ubuntu (те саме середовище, що в тікеті). Для
розробки `parser`/`web` на macOS — `README.mac.md`.

## Структура репозиторію

```
local/                        # Мережа A (SITL-хост)
├── provision.sh               # одноразовий провіжн SITL-хоста (sudo)
├── setup-wireguard.sh          # клієнтський бік тунелю (ручний обмін ключами)
├── run-sitl.sh                  # повторюваний запуск SITL+MAVProxy (без sudo)
├── push-logs.sh                 # автоматична доставка логів на VPS (фон, запускається run-sitl.sh)
└── keyboard_adapter/              # MAVProxy-модуль: клавіатура -> MANUAL_CONTROL
vps/                        # Мережа B (VPS)
├── provision.sh                # одноразовий провіжн VPS: Docker, ufw, збірка образів
│                               # і `docker compose up -d` — все в одному прогоні
├── setup-wireguard.sh           # серверний бік тунелю (запускається людиною на VPS)
├── services/
│   ├── parser/                   # приймач + аналізатор логів (Python, pymavlink)
│   └── web/                       # звіт (Astro/TS)
└── compose/                      # docker-compose.yml, Caddyfile, .env.example
docs/
├── demo-flight-task.md          # програма польоту для 3+ залікових польотів
├── host-prerequisites.md        # чернетка, з якої зібрано розділ SITL нижче
└── scoring-algorithm.md         # алгоритм вердикту (if/else за порогами)
```

`local/` — усе, що працює на SITL-хості (Мережа A); `vps/`, включно з самими
сервісами (`vps/services/`), — усе, що працює на VPS (Мережа B). Назва теки
відповідає мережі, а не типу артефакту (скрипт/сервіс) — `parser`/`web` ніде, крім VPS,
не запускаються, тож логічно є частиною `vps/`, а не окремою верхньорівневою текою.

`local/provision.sh` і `vps/provision.sh` — однакова назва файлу навмисно: та сама
роль (одноразовий, sudo, ідемпотентний провіжн), той самий патерн, різні хости. Обидва
запускаються з клона репозиторія на своєму хості — жодних кроків з робочої машини.
WireGuard між ними піднімає окремий `local/setup-wireguard.sh`/`vps/setup-wireguard.sh` —
не частина жодного з двох провіжнів (крок 3 нижче).

## Крок 1. Мережа A — SITL-хост

Клонувати репозиторій на чисту Ubuntu VM (або bare-metal):

```bash
sudo apt-get install -y git   # якщо git ще нема
git clone <URL_РЕПОЗИТОРІЮ>
cd <ТЕКА_РЕПОЗИТОРІЮ>
```

### 1.1. Одноразовий провіжн

```bash
./local/provision.sh
```

Один `sudo`-запит. Клонує **офіційний апстрім** ArduPilot (не форк) у гітигнорену
`.sitl/`, виставляє тег `Plane-4.6.3` (перевизначити: `ARDUPILOT_TAG=... ./local/provision.sh`),
запускає ArduPilot-івський `install-prereqs-ubuntu.sh` (ставить MAVProxy/pymavlink у
`~/venv-ardupilot`, компілює wxPython — 20-40+ хв першого разу), додає
`wireguard-tools`/`rsync`/`openssh-client`/`git-lfs`/`inotify-tools` (доставка логів) і
групу `input` (клавіатурний бекенд `evdev`). WireGuard ще НЕ піднімається тут — крок 3.

### 1.2. Перевірка

Скрипт сам друкує в кінці, чи юзер уже в групі `input`. Якщо ні (група щойно додана
цим самим прогоном) — **вийти й зайти знову** (або `newgrp input` у поточному
терміналі) перед кроком 4, інакше `keyboard_adapter` впаде на правах доступу до
`/dev/input`:

```bash
groups | tr ' ' '\n' | grep -x input && echo "OK" || echo "потрібен релогін"
```

## Крок 2. Мережа B — VPS

Клонувати той самий репозиторій на VPS:

```bash
ssh root@<vps>
apt-get install -y git   # якщо git ще нема
git clone <URL_РЕПОЗИТОРІЮ>
cd <ТЕКА_РЕПОЗИТОРІЮ>
```

### 2.1. Одноразовий провіжн

```bash
./vps/provision.sh
```

Все в одному прогоні: Docker Engine (офіційний apt-репозиторій), `wireguard-tools`,
`ufw` (22/80/443/51820-udp), теки `/srv/app/data/{inbox,results}`, self-signed
TLS-сертифікат у `/srv/app/certs/{server.crt,server.key}` (якщо там ще нічого нема —
див. розділ «Сертифікат HTTPS» нижче), і одразу **збірка образів `parser`/`web` та
`docker compose up -d`** — усе тут же, на самому VPS (він уже нативний `amd64`, тож
крос-збірка/перенесення образів іншим шляхом не потрібні). WireGuard ще НЕ піднімається
тут — крок 3. Ідемпотентний — повторний прогін (напр. після `git pull` з новим кодом)
сам пересобере й перезапустить контейнери.

### 2.2. Перевірка

```bash
curl http://localhost/          # з самого VPS — має відповідати HTML звіту
curl -k https://localhost/      # -k: доки сертифікат self-signed
sudo docker compose --project-directory vps/compose -f vps/compose/docker-compose.yml ps
```

Зовнішньо — `http://<ip_або_домен_vps>/` і `https://<ip_або_домен_vps>/` (браузер
покаже попередження про self-signed сертифікат, доки не підставлений реальний).

## Сертифікат HTTPS

За замовчуванням `vps/provision.sh` генерує **self-signed** сертифікат
(`/srv/app/certs/server.crt`+`server.key`) — лише якщо в цій теці ще нічого нема. Це
дозволяє критерію "звіт відкривається по HTTPS" виконуватись одразу, без залежності від
того, коли з'явиться реальний домен/сертифікат.

Щоб підставити реальний сертифікат:

```bash
sudo cp <fullchain.pem_або_your.crt> /srv/app/certs/server.crt
sudo cp <privkey.pem_або_your.key> /srv/app/certs/server.key
sudo chown 1000:1000 /srv/app/certs/*
./vps/provision.sh   # повторний прогін: бачить, що файли вже є, self-signed не чіпає
```

`Caddyfile` і сам скрипт міняти не треба — вони завжди читають ті самі два файли за тими
самими іменами, незалежно від того, self-signed вони чи реальні.

## Крок 3. WireGuard-тунель

**SITL-хост ніколи не ходить по SSH на публічну адресу VPS** — лише крізь сам тунель,
після його підняття, і то лише `push-logs.sh` на `root@10.10.0.1`. Обмін публічними
ключами (WireGuard і SSH-ключ `push-logs.sh`) робить людина — двома способами:

**Спосіб А — повністю вручну, з двох терміналів** (немає жодного доступу, що бачить
одразу обидва хости):

```bash
# 1. На SITL-хості: друкує публічний ключ клієнта (WireGuard) і публічний
#    SSH-ключ push-logs.sh, wg0 ще НЕ піднятий
./local/setup-wireguard.sh

# 2. На VPS (будь-яким доступом): додає SSH-ключ push-logs.sh у
#    /root/.ssh/authorized_keys, друкує публічний ключ сервера (WireGuard)
CLIENT_WG_PUBKEY=<WireGuard-ключ_з_1> CLIENT_SSH_PUBKEY=<SSH-ключ_з_1> \
  ./vps/setup-wireguard.sh

# 3. На SITL-хості: тепер піднімає wg0 і перевіряє root@10.10.0.1 (push-logs.sh) без пароля
SERVER_WG_PUBKEY=<ключ_з_2> VPS_ENDPOINT=<ip_або_домен_vps>:51820 ./local/setup-wireguard.sh
```

**Спосіб Б — з третьої машини, яка має SSH-доступ до обох хостів** (наприклад,
робоча машина адміністратора): та сама послідовність команд, просто виконується не за
двома терміналами вручну, а однією людиною/сесією, яка бачить весь контекст одразу —
результат кожної команди одразу підставляється в наступну, без копіювання між
терміналами:

```bash
CLIENT_OUT="$(ssh sitl-host 'cd <ТЕКА_РЕПОЗИТОРІЮ> && ./local/setup-wireguard.sh')"
CLIENT_WG_PUBKEY="$(echo "$CLIENT_OUT" | sed -n 's/^Публічний ключ клієнта (WireGuard): //p')"
CLIENT_SSH_PUBKEY="$(echo "$CLIENT_OUT" | sed -n 's/^Публічний SSH-ключ push-logs.sh: //p')"

SERVER_WG_PUBKEY="$(ssh root@vps-host \
  "cd <ТЕКА_РЕПОЗИТОРІЮ> && CLIENT_WG_PUBKEY='$CLIENT_WG_PUBKEY' CLIENT_SSH_PUBKEY='$CLIENT_SSH_PUBKEY' ./vps/setup-wireguard.sh")"

ssh sitl-host "cd <ТЕКА_РЕПОЗИТОРІЮ> && SERVER_WG_PUBKEY='$SERVER_WG_PUBKEY' VPS_ENDPOINT=<ip_або_домен_vps>:51820 ./local/setup-wireguard.sh"
```

Обидва способи ідемпотентні (повторний прогін перезапише конфіги обох боків і перепідніме
`wg0`); `CLIENT_SSH_PUBKEY` додається в `authorized_keys` на VPS лише якщо його там ще
нема. Після кроку 3 SSH-ключ `push-logs.sh` уже авторизований на VPS — щойно тунель
підніметься, `root@10.10.0.1` одразу доступний без пароля (перевіряється в кінці кроку
3 автоматично).

## Крок 4. Запуск SITL + MAVProxy + керування

На SITL-хості, у терміналі:

```bash
./local/run-sitl.sh
```

Команда піднімає SITL ArduPlane, MAVProxy (`--console --map`) з модулями
`keyboard_adapter` і `horizon` (авіагоризонт, окреме wx-вікно), і у фоні `push-logs.sh`
(автоматична доставка логів на VPS через уже піднятий тунель). Відкриються два додаткові
вікна (карта, авіагоризонт) — сам термінал, у якому виконана команда, лишається
консоллю MAVProxy з prompt'ом `MAV>` — **саме в цьому терміналі**, не в новому окремому
вікні, вводяться команди для наступного кроку. `.BIN`/`.tlog` пишуться в
`.sitl/ArduPlane/logs/`.

Клавіатурне керування (замість джойстика — обґрунтування в `local/keyboard_adapter/README.md`):

| Клавіші | Вісь |
|---|---|
| `W` / `S` | pitch |
| `A` / `D` | roll |
| `Q` / `E` | yaw |
| `Up` / `Down` | throttle (утримується, без spring-return) |

Тротл свідомо на `Up`/`Down`, не `Shift`/`Ctrl`: `evdev` читає клавіші сиро, незалежно
від фокуса вікна — `Shift`/`Ctrl` як модифікатори під час друку команд у `MAV>`-консолі
заодно рухали б тротл.

Керування клавіатурою вмикається **явно**, окремою командою в тій самій консолі
`MAV>` (клацнути в термінал, щоб фокус був там, і вводити рядки один за одним,
Enter після кожного) — недостатньо просто озброїтись і бути в `FBWA`:

```
mode FBWA
arm throttle
kb on      # клавіатура НЕ керує, доки не введено цю команду
```

`kb off`, вихід із `FBWA` чи `disarm` — будь-яке з цього зупиняє керування. Завершення
сесії: `disarm`, потім `Ctrl+C` (зупиняє SITL, MAVProxy і всі модулі разом).

Якщо автовизначення клавіатури обрало не той `/dev/input/eventN` —
`KEYBOARD_DEVICE=/dev/input/eventN ./local/run-sitl.sh` (`ls /dev/input/by-id/` для пошуку).

## Крок 5. Політ і звіт

1. У консолі `MAV>` (той самий термінал, що і крок 4): `mode FBWA` → `arm throttle` →
   `kb on` → пілотувати за програмою польоту (`docs/demo-flight-task.md`).
2. `disarm`, потім `Ctrl+C` у тому ж терміналі — завершує сесію.
3. Лог (`.BIN`, закритий на дизармі) автоматично потрапляє на VPS через `push-logs.sh`
   (фон, запущений `run-sitl.sh`) — жодної ручної команди після польоту не потрібно.
4. Відкрити `https://<vps>/` — новий політ з'являється у списку (з бейджем вердикту)
   протягом секунди (клієнтський поллінг), звіт по кліку показує графік стіків поверх
   attitude, гістограму амплітуд і зведені метрики з підсумковою оцінкою.
5. Повторити щонайменше 3 рази для здачі — **тією ж програмою польоту** (інакше метрики
   різних польотів непорівнянні).

## Ключові рішення й обмеження

- **Клавіатура замість джойстика** — узгоджено окремо; spring-return на roll/pitch/yaw,
  щоб клавіатурний ввід не спотворював метрики амплітуди/різкості.
- **keyboard-адаптер — MAVProxy-модуль**, не окремий процес: ідіоматично для MAVProxy
  (так само map/console), без власного UDP-конекту. Компроміс: падіння самого MAVProxy
  тепер тягне за собою й керування (падіння окремого модуля — ні).
  - Клавіатурний бекенд — лише `evdev` (Xorg і Wayland однаково; тротл на `Up`/`Down`, не
    `Shift`/`Ctrl` — не заплутуються з друком команд у консолі).
  - Керування вмикається лише в `FBWA` + armed + явний `kb on` — жодна з двох перших умов
    сама по собі (можна виникнути на землі/під час рулювання) не запускає керування.
- **`horizon`** (штатний MAVProxy-модуль) — доданий для живого фідбека тангажа/крену під
  час пілотування; `speech`/`graph` розглядались і відхилені (зайва вага без вигоди).
- **Розгортання — shell (`local/provision.sh` + `vps/provision.sh`), не Ansible.**
  Один VPS, одноразовий прогін — цінність Ansible (ідемпотентність для флоту хостів) тут
  не окупається. Обидва скрипти запускаються з клона репозиторія на своєму хості.
- **WireGuard — окремі симетричні скрипти (`local/setup-wireguard.sh` +
  `vps/setup-wireguard.sh`), не частина жодного `provision.sh`.** SITL-хост не ходить
  по SSH на публічну адресу VPS — обмін ключами завжди ручний (крок 3), або одним і
  тим самим доступом з третьої машини, якщо така є.
- **Образи для VPS збираються прямо на самому VPS**, під час `vps/provision.sh` —
  VPS уже нативний `amd64`, окремого кроку "зібрати на робочій машині й перенести" нема.
- **`local/provision.sh` shallow-клонує ArduPilot** (`--depth 1 --branch <тег>`), не
  всю історію апстріму — SITL-збірці історія не потрібна, а репозиторій ArduPilot
  великий (десятки тисяч комітів, багато тегів).
- **Self-signed сертифікат за замовчуванням** — критерій "звіт по HTTPS" виконується
  одразу; реальний сертифікат підставляється без зміни коду (розділ «Сертифікат HTTPS»).
- **Доставка логів — автоматична** (`local/push-logs.sh`, `inotifywait` на `close_write`),
  не окрема ручна команда після кожного польоту.
- **Вердикт — if/else за конфігом порогів, без LLM.** Пороги — на клієнті (браузер рахує
  категорію миттєво, сервер віддає лише метрики + дефолтні пороги).
- **`crashed` — окрема категорія, що переважає над good/warning/bad** — `STAT.Crash` сам
  по собі не годиться (не спрацьовує в ручних режимах), тож комбінується з евристикою.
- **Пороги вердикту** (`vps/services/parser/thresholds.yaml`) — placeholder з демо-польоту;
  замінюються реальними good/bad-шаблонами без зміни коду, лише конфіг.
- **Програма польоту** (`docs/demo-flight-task.md`) — та сама послідовність фаз для
  всіх 3+ залікових польотів, щоб метрики між ними лишались порівнюваними.

## Траблшутинг

Реальні проблеми, на які натрапили під час живого прогону (`SITL-test`/`VPS-test`),
і як їх розпізнати/виправити.

**`ПОМИЛКА: http://localhost/ не відповідає` одразу після `vps/provision.sh`.**
Холодний старт: `docker compose up -d` повертається одразу, але Node (`web`) і Caddy
ще кілька секунд стартують (перший запуск — довше). Сам `vps/provision.sh` тепер
чекає до 30с (`curl` з ретраями). Якщо все одно не відповідає — `sudo docker compose ps`/
`sudo docker compose logs web caddy` у `vps/compose/`; типова причина — `web` ще не встиг
відкрити порт (у логах буде `[@astrojs/node] Server listening on ...` — якщо цього
рядка нема, чекати довше або дивитись помилку вище в логах).

**`wg show` показує peer, `latest handshake` — порожній, `transfer: 0 B received`.**
Найімовірніша причина — публічний ключ передрукований вручну з екрана/скріншота і
містить помилку (класика: `I`/`l`/`1`, `O`/`0` виглядають однаково в моноширинному
шрифті). WireGuard на такий "майже правильний" ключ мовчки не встановлює з'єднання —
жодної помилки, просто нуль трафіку. Лікування: **ніколи не передруковувати ключ
руками** — забирати його командою (командна підстановка `$(...)`, як у кроці 3, спосіб
Б), без ручного набору. Якщо ключі точно збігаються, а handshake все одно нема —
перевірити `sudo ufw status` на VPS (`51820/udp` має бути `ALLOW`) і що
`VPS_ENDPOINT`/`Endpoint` дійсно вказує на адресу, яка слухає `51820/udp` ззовні.

**`WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` при SSH на VM.** Типово після
відкату VM до снепшоту чи переустановки — SSH-ключ хоста змінився, `known_hosts`
застарів. `ssh-keygen -R <ip_або_host>` прибирає старий запис, наступний SSH підключиться
й запам'ятає новий (з `-o StrictHostKeyChecking=accept-new` за потреби, без інтерактивного
підтвердження).

**`Permission denied (publickey)` при спробі скрипта зайти по SSH на VPS.** Означає, що
цей SSH-доступ ще не авторизований на цільовому хості — додати відповідний публічний
ключ у `~/.ssh/authorized_keys` цільового користувача заздалегідь (це якраз і є суть
кроку 3: SITL-хост власного SSH-доступу до VPS не отримує взагалі, лише публічні ключі
передаються вручну/третьою машиною).
