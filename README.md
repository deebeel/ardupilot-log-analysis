# Стенд SITL + сервіс аналізу якості пілотування

Тестове завдання RND-254. Інструкція нижче написана так, щоб її можна було виконати
крок за кроком у терміналі, навіть якщо ти не системний адміністратор — просто вводиш
команди в тому порядку, в якому вони йдуть, і читаєш, що кожна робить.

## Перед тим, як почати — кілька термінів

- **Термінал** — чорне вікно, де вводиш текстові команди замість клацання мишкою.
  Усі команди нижче — саме туди.
- **SSH** — спосіб зайти в термінал на іншому комп'ютері (наприклад, на VPS у
  хмарі) зі свого, через інтернет. Команда виглядає як `ssh юзер@адреса`; після неї
  термінал "переноситься" на той інший комп'ютер, доки не введеш `exit` чи закриєш
  вікно.
- **VPS** — комп'ютер у хмарі (орендований сервер), до якого заходиш по SSH.
- **`sudo`** — префікс перед командою, який каже "виконай це з правами
  адміністратора"; система попросить твій пароль.
- **WireGuard-тунель** — приватний, зашифрований "канал" між двома комп'ютерами
  через інтернет, як окремий приватний провід між ними. У цьому проєкті лог-файли
  й телеметрія ходять лише через нього — навпростець через звичайний інтернет вони
  не потрапляють.
- **Docker / `docker compose`** — спосіб запускати програми (тут: `parser` і `web`)
  у ізольованих "коробках" (контейнерах), без установки їхніх залежностей прямо на
  систему. `docker compose up -d` = "зібрати ці коробки і запустити їх у фоні".
- **Self-signed сертифікат** — "самопідписаний" сертифікат для HTTPS. Браузер
  покаже попередження "сайт не безпечний" — це очікувано і не помилка (пояснення —
  розділ «Сертифікат HTTPS» нижче); просто підтверджуєш, що довіряєш, і йдеш далі.

Стенд складається з двох окремих комп'ютерів (не обов'язково фізичних — можуть бути
віртуальними машинами), з'єднаних WireGuard-тунелем:

- **Мережа A (SITL-хост)** — окрема Ubuntu-машина (віртуальна машина або звичайний
  комп'ютер): тут симулюється сам літак (SITL ArduPlane), тут же — вікно керування
  (MAVProxy: карта + консоль + авіагоризонт) і клавіатурний адаптер (керуєш
  клавіатурою замість джойстика).
- **Мережа B (VPS)** — окремий Ubuntu-сервер у хмарі, до якого є SSH-доступ і
  DNS-ім'я (адреса типу `mydomain.com`, а не лише IP): приймає лог-файли польотів
  (`parser`) і показує звіт у браузері (`web`), обидва запущені в Docker за Caddy
  (веб-сервером, який віддає сторінки по HTTP і HTTPS).

Це канонічна інструкція — покриває лише Ubuntu (те саме середовище, що в тікеті).

## Структура репозиторію

```
local/                        # Мережа A (SITL-хост)
├── provision.sh               # одноразова підготовка SITL-хоста (sudo)
├── setup-wireguard.sh          # піднімає тунель з боку SITL-хоста (ручний обмін ключами)
├── run-sitl.sh                  # запускається перед кожним польотом (без sudo)
├── push-logs.sh                 # автоматична доставка логів на VPS (фон, запускається run-sitl.sh)
└── keyboard_adapter/              # частина MAVProxy: клавіатура -> керування літаком
vps/                        # Мережа B (VPS)
├── provision.sh                # одноразова підготовка VPS: Docker, файрвол, збірка й запуск сервісів
├── setup-wireguard.sh           # піднімає тунель з боку VPS (запускається людиною на VPS)
├── services/
│   ├── parser/                   # приймає й аналізує лог-файли (Python, pymavlink)
│   └── web/                       # звіт, який видно в браузері (Astro/TS)
└── compose/                      # налаштування Docker (docker-compose.yml, Caddyfile)
docs/
├── demo-flight-task.md          # орієнтовна програма польоту для 3+ залікових польотів
└── scoring-algorithm.md         # як рахується підсумкова оцінка польоту
```

`local/` — усе, що запускається на SITL-хості; `vps/` — усе, що запускається на VPS
(включно з самими програмами `parser`/`web`, бо вони ніде більше й не запускаються).

`local/provision.sh` і `vps/provision.sh` — однакова назва навмисно: та сама роль
(одноразова підготовка хоста, один запит пароля через `sudo`), той самий підхід, різні
машини. Обидва запускаються прямо на своєму хості (після того, як туди клонований цей
репозиторій) — жодних команд зі своєї робочої машини для цього не треба.

## Крок 1. Мережа A — SITL-хост

Тут потрібен доступ до термінала самої SITL-машини (VM чи звичайного комп'ютера) —
або сидиш за ним фізично, або заходиш по SSH, якщо він уже налаштований для
віддаленого доступу.

Клонувати (скопіювати) цей репозиторій на чисту Ubuntu-машину:

```bash
sudo apt-get install -y git   # якщо команда git ще не встановлена
git clone https://github.com/deebeel/ardupilot-log-analysis.git
cd ardupilot-log-analysis
```

### 1.1. Одноразова підготовка

```bash
./local/provision.sh
```

Ця команда попросить твій пароль один раз (через `sudo`) і встановить усе потрібне:
завантажить **офіційний** симулятор ArduPilot (не якийсь форк) у теку `.sitl/`,
поставить MAVProxy й інші системні пакети (близько 20-40 хвилин на перший запуск —
компілюється велика бібліотека wxPython), а також додасть твого користувача в групу
`input` (потрібно, щоб клавіатура працювала як джерело керування). WireGuard-тунель
тут ще НЕ піднімається — це крок 3.

### 1.2. Перевірка

Наприкінці скрипт сам напише, чи твій користувач уже в групі `input`. Якщо каже, що
потрібен релогін (група щойно додана) — **вийди з термінала й зайди знову** (або
введи `newgrp input` у поточному вікні) перед кроком 4. Перевірити ще раз можна так:

```bash
groups | tr ' ' '\n' | grep -x input && echo "OK" || echo "потрібен релогін"
```

Якщо вивело `OK` — усе гаразд, можна йти далі.

## Крок 2. Мережа B — VPS

Тепер потрібен доступ до VPS — заходимо туди по SSH (адресу/IP і пароль чи ключ для
входу дає той, хто орендував VPS):

```bash
ssh root@<адреса_або_IP_VPS>
```

Далі — усередині цього SSH-з'єднання (тобто термінал уже "переїхав" на VPS):

```bash
apt-get install -y git   # якщо команда git ще не встановлена
git clone https://github.com/deebeel/ardupilot-log-analysis.git
cd ardupilot-log-analysis
```

### 2.1. Одноразова підготовка

```bash
./vps/provision.sh
```

Один прогін ставить усе: Docker, `ufw` (файрвол — відкриває лише потрібні порти:
22 для SSH, 80 і 443 для веб-сторінки, 51820 для WireGuard), self-signed
TLS-сертифікат (див. розділ «Сертифікат HTTPS» нижче), і одразу збирає й запускає
самі сервіси (`parser`+`web`+`caddy`) командою `docker compose up -d`. WireGuard тут
ще НЕ піднімається — крок 3. Команду можна запускати повторно (наприклад, після
`git pull` з новим кодом) — вона сама пересобере й перезапустить усе, що змінилось.

### 2.2. Перевірка

Ще всередині SSH-сесії на VPS:

```bash
curl http://localhost/          # має вивести шматок HTML-сторінки
curl -k https://localhost/      # те саме по HTTPS (-k: доки сертифікат self-signed)
sudo docker compose --project-directory vps/compose -f vps/compose/docker-compose.yml ps
```

Останній рядок цієї команди має показати три контейнери (`web`, `parser`, `caddy`) зі
статусом `running`/`Up`.

Тепер, уже зі свого звичайного браузера (не в терміналі) — відкрити
`http://<ip_або_домен_vps>/` і `https://<ip_або_домен_vps>/`. Браузер покаже
попередження про ненадійний сертифікат на HTTPS-версії — це очікувано (self-signed),
підтверджуєш і йдеш далі.

## Сертифікат HTTPS

Щоб сторінка звіту відкривалась по HTTPS одразу, `vps/provision.sh` сам створює
**self-signed** сертифікат (два файли: `/srv/app/certs/server.crt` і
`/srv/app/certs/server.key`) — але лише якщо там ще нічого немає. Якщо пізніше
з'явиться справжній сертифікат (наприклад, від Let's Encrypt чи хостера) — просто
поклади його файли під тими самими іменами в ту саму теку:

```bash
sudo cp <твій_сертифікат.pem_або_.crt> /srv/app/certs/server.crt
sudo cp <твій_приватний_ключ.pem_або_.key> /srv/app/certs/server.key
sudo chown 1000:1000 /srv/app/certs/server.crt /srv/app/certs/server.key
./vps/provision.sh   # запустити ще раз: побачить, що файли вже є, і не чіпатиме їх
```

Нічого більше змінювати не треба — Caddy (веб-сервер) завжди читає ці самі два файли,
незалежно від того, self-signed вони чи справжні.

## Крок 3. З'єднання двох машин (WireGuard)

Тут найважливіше правило: **SITL-хост ніколи сам не заходить по SSH на VPS через
звичайний інтернет** — лише через сам тунель, і то тільки одна конкретна команда
(`push-logs.sh`, автоматична доставка логів). Тому обмін "ключами" (секретними
рядками, якими домовляються два боки тунелю) виконує людина — двома способами.

**Спосіб А — вручну, з двох окремих терміналів** (якщо в тебе немає одного доступу,
який бачить одразу обидві машини):

```bash
# 1. У терміналі SITL-хоста: команда виведе на екран два рядки — публічний ключ
#    WireGuard і публічний SSH-ключ для push-logs.sh. Сам тунель ще НЕ піднятий.
./local/setup-wireguard.sh

# 2. У терміналі VPS (по SSH, як у кроці 2): встав сюди ключі, які надрукувала
#    команда вище (замінивши <...> нижче). Ця команда додасть SSH-ключ у список
#    довірених на VPS і надрукує третій ключ — публічний ключ сервера.
CLIENT_WG_PUBKEY=<WireGuard-ключ_з_1> CLIENT_SSH_PUBKEY=<SSH-ключ_з_1> \
  ./vps/setup-wireguard.sh

# 3. Знову в терміналі SITL-хоста: встав ключ сервера з кроку 2 і адресу VPS.
#    Ця команда вже піднімає сам тунель і перевіряє, що все з'єдналось.
SERVER_WG_PUBKEY=<ключ_з_2> VPS_ENDPOINT=<ip_або_домен_vps>:51820 ./local/setup-wireguard.sh
```

**Спосіб Б — з третьої машини, яка сама має SSH-доступ до обох** (наприклад, твій
власний ноутбук, якщо з нього можна зайти і на SITL-хост, і на VPS): та сама
послідовність із трьох команд, просто виконується однією людиною в одному місці —
результат кожної команди підставляється в наступну автоматично, без переписування
руками:

```bash
CLIENT_OUT="$(ssh sitl-host 'cd ardupilot-log-analysis && ./local/setup-wireguard.sh')"
CLIENT_WG_PUBKEY="$(echo "$CLIENT_OUT" | sed -n 's/^Публічний ключ клієнта (WireGuard): //p')"
CLIENT_SSH_PUBKEY="$(echo "$CLIENT_OUT" | sed -n 's/^Публічний SSH-ключ push-logs.sh: //p')"

SERVER_WG_PUBKEY="$(ssh root@vps-host \
  "cd ardupilot-log-analysis && CLIENT_WG_PUBKEY='$CLIENT_WG_PUBKEY' CLIENT_SSH_PUBKEY='$CLIENT_SSH_PUBKEY' ./vps/setup-wireguard.sh")"

ssh sitl-host "cd ardupilot-log-analysis && SERVER_WG_PUBKEY='$SERVER_WG_PUBKEY' VPS_ENDPOINT=<ip_або_домен_vps>:51820 ./local/setup-wireguard.sh"
```

(`sitl-host` і `vps-host` тут — назви, які треба замінити на реальні `юзер@адреса`
кожної машини, або налаштувати заздалегідь у `~/.ssh/config`.)

В обох способах команду можна безпечно запускати повторно (наприклад, якщо змінилась
адреса VPS) — вона просто оновить налаштування й перепідніме тунель. Після кроку 3
`push-logs.sh` уже може заходити на VPS без пароля через тунель — це перевіряється
автоматично в кінці команди з кроку 3.

## Хто за що відповідає на SITL-хості

| Роль | Що робить | Чим закривається |
|---|---|---|
| **SITL** | сама фізика польоту, "мозок" літака | програма `sim_vehicle.py` (ArduPlane 4.6) |
| **GCS + візуалізація** | показує телеметрію, HUD, режими, карту | MAVProxy (`--map --console`) |
| **Клавіатурний адаптер** | перетворює натискання клавіш на керування літаком | `local/keyboard_adapter` |
| **Авіагоризонт** | окреме вікно з "живим" креном/тангажем під час польоту | модуль MAVProxy `horizon` |

## Крок 4. Запуск SITL і керування

На SITL-хості, у звичайному (не SSH) терміналі цієї машини:

```bash
./local/run-sitl.sh
```

Ця команда запускає все одразу: сам симулятор літака, вікна карти й авіагоризонту, і
у фоні — автоматичну доставку логів на VPS. Відкриються два додаткові вікна (карта,
авіагоризонт) — а сам термінал, у якому ти запустив команду, перетвориться на консоль
з написом `MAV>` на початку рядка. **Саме в цей термінал**, а не в нове вікно, ти
вводитимеш команди керування польотом (крок 5).

Керуєш літаком клавіатурою (замість джойстика):

| Клавіші | Що робить |
|---|---|
| `W` / `S` | ніс вгору / вниз (pitch) |
| `A` / `D` | крен вліво / вправо (roll) |
| `Q` / `E` | поворот вліво / вправо (yaw) |
| `↑` / `↓` | газ більше / менше (throttle — тримається на місці, не пружинить назад) |

Якщо клавіатура не реагує — можливо, комп'ютер вибрав не той пристрій автоматично.
Список пристроїв: `ls /dev/input/by-id/`; вказати правильний вручну:
`KEYBOARD_DEVICE=/dev/input/eventN ./local/run-sitl.sh`.

## Крок 5. Політ і звіт

У тому самому терміналі з написом `MAV>` (той, що лишився відкритим після кроку 4)
вводь рядки один за одним, натискаючи Enter після кожного:

```
mode FBWA
arm throttle
kb on
```

`mode FBWA` — переключає літак у режим напівавтоматичного ручного керування.
`arm throttle` — "заводить двигун" (без цього літак не рухається). `kb on` — увімкнути
керування з клавіатури: **без цієї команди клавіші нічого не роблять**, навіть якщо
режим і "заведення" вже готові — це свідомий запобіжник.

1. Після `kb on` — керуй за програмою польоту (`docs/demo-flight-task.md`).
2. Щоб закінчити політ: введи `disarm`, потім натисни `Ctrl+C` у тому самому
   терміналі — це зупиняє все одразу (симулятор, вікна, керування).
3. Лог-файл польоту сам, автоматично, вже їде на VPS (те, що робилось у фоні з
   кроку 4) — жодної додаткової команди вводити не треба.
4. Відкрий у браузері `https://<адреса_vps>/` — новий політ з'явиться у списку
   (з кольоровою позначкою оцінки) протягом секунди. Клік на нього — і відкриється
   звіт: графік рухів стіків, гістограма амплітуд і підсумкові цифри.
5. Повтори весь цей крок ще мінімум 2 рази (разом — 3+ польоти) — **за тією самою
   програмою польоту щоразу**, інакше цифри різних польотів не можна буде порівняти
   між собою.

Якщо на VPS налаштована інша адреса/юзер/тека для доставки логів (не дефолтна) —
перед кроком 4 (`run-sitl.sh`) можна задати `VPS_WG_HOST` (дефолт `10.10.0.1`),
`VPS_USER` (`root`), `VPS_INBOX` (`/srv/app/data/inbox`) як змінні середовища.

## Ключові рішення й обмеження

- **Клавіатура замість джойстика** — узгоджено окремо; плавне наростання й
  повернення до нейтралі (spring-return) на крені/тангажі/розвороті, щоб клавіатурний
  ввід не спотворював метрики амплітуди й різкості рухів.
- **Клавіатурний адаптер — частина MAVProxy** (модуль, не окрема програма): так само,
  як карта чи консоль. Компроміс: якщо впаде сам MAVProxy — керування теж зупиниться
  (падіння лише одного окремого модуля — ні).
  - Клавіатурний бекенд — лише `evdev` (працює однаково на старіших і новіших версіях
    графічної підсистеми Ubuntu; газ — на стрілках, а не `Shift`/`Ctrl`, щоб не
    заважати друку команд у консолі).
  - Керування вмикається лише коли одразу три умови зійшлись: режим `FBWA`, апарат
    "заведений" (armed), і явно введена команда `kb on` — жодна з перших двох сама по
    собі керування не запускає.
- **`horizon`** (модуль MAVProxy) — додає живий авіагоризонт під час пілотування.
- **Розгортання — прості shell-скрипти, не Ansible.** Для одного VPS і одноразового
  налаштування Ansible додав би складність без реальної вигоди.
- **WireGuard-тунель піднімається окремими скриптами**, не частиною основної
  підготовки хоста — SITL-хост не заходить по SSH на публічну адресу VPS, обмін
  ключами завжди вручну (крок 3) або через третю машину з доступом до обох.
- **Образи Docker для VPS збираються прямо на самому VPS** під час підготовки —
  без окремого кроку "зібрати на своєму комп'ютері й перенести".
- **Self-signed сертифікат за замовчуванням** — сторінка звіту відкривається по
  HTTPS одразу; справжній сертифікат підставляється без зміни коду (розділ
  «Сертифікат HTTPS»).
- **Доставка логів на VPS — повністю автоматична**, без ручних команд після польоту.
- **Оцінка польоту рахується простими правилами (якщо-то), без штучного інтелекту.**
  Пороги оцінки можна підлаштувати прямо в браузері під час перегляду звіту.
- **Категорія "аварія" завжди переважає** над "добре"/"попередження"/"погано" —
  визначається і вбудованим детектором ArduPilot, і власною перевіркою (малий
  висоту + екстремальний кут наприкінці лога).
- **Пороги оцінки** (`vps/services/parser/thresholds.yaml`) — тимчасові приблизні
  значення; замінюються реальними без зміни коду, лише одним конфіг-файлом.
- **Орієнтовна програма польоту** (`docs/demo-flight-task.md`) — та сама послідовність фаз для
  всіх 3+ залікових польотів.

## Фінальна перевірка стенду

Перед тим, як записувати заліковий політ, варто пройти цей список — це реальні
речі, які можуть зламати сценарій, а не просто "команда відпрацювала без помилок":

1. Клавіатура реально працює (перевір рухи стіків після `kb on`).
2. MAVProxy бачить симулятор, `--map` показує рух літака.
3. У консолі MAVProxy команда `module list` показує `keyboard_adapter` і `horizon`
   завантаженими; вікно `horizon` відкрилось окремо.
4. Без `kb on` клавіші НЕ рухають літак, навіть у `FBWA` і armed; після `kb on` —
   рухають. Вихід із `FBWA`, `disarm` чи `kb off` одразу зупиняють керування.
5. Вікно `horizon` реально показує той самий крен/тангаж, що й на карті.
6. Після `disarm` новий лог реально з'являється на VPS (перевірити командою
   `ssh <vps> ls /srv/app/data/inbox/`) — сам, без ручних команд.

## Траблшутинг

Реальні проблеми, на які натрапили під час живого прогону, і як їх розпізнати чи
виправити.

**`ПОМИЛКА: http://localhost/ не відповідає` одразу після `vps/provision.sh`.**
Просто холодний старт: контейнери щойно запустились, і їм потрібно кілька секунд.
Скрипт сам чекає до 30 секунд і пробує знову. Якщо все одно не відповідає —
подивитись, що відбувається, командою `sudo docker compose ps` і
`sudo docker compose logs web caddy` (виконати в теці `vps/compose/`).

**Команда `wg show` (стан тунелю) показує з'єднання, але `handshake` порожній,
трафік — `0 B`.** Найімовірніша причина — один із ключів передрукований руками з
екрана й містить помилку (літери `I`/`l`/`1`, `O`/`0` виглядають однаково). WireGuard
на такий "майже правильний" ключ просто мовчки не з'єднується — без жодної помилки.
Лікування: **ніколи не передруковувати ключ руками** — копіювати текст цілком (або
командою, як у способі Б кроку 3). Якщо ключі точно правильні, а з'єднання все одно
нема — перевірити `sudo ufw status` на VPS (рядок `51820/udp` має бути `ALLOW`) і що
адреса, яку вказали як `VPS_ENDPOINT`, справді належить цьому VPS.

**`WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` під час SSH.** З'являється,
якщо машина, до якої заходиш, була переустановлена чи відкочена до збереженого стану
(тоді в неї новий "відбиток" для SSH). Команда `ssh-keygen -R <адреса>` прибирає
старий запис — наступний SSH-вхід запам'ятає новий.

**`Permission denied (publickey)` під час спроби скрипта зайти по SSH на VPS.**
Означає, що цей конкретний доступ ще не "довірений" на VPS. Треба, щоб відповідний
публічний ключ був заздалегідь доданий у список довірених на VPS (`authorized_keys`) —
саме це і є суть кроку 3: SITL-хост власного SSH-доступу до VPS не отримує взагалі,
лише окремі публічні ключі передаються вручну чи через третю машину.
