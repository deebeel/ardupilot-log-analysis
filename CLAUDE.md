**Стек**
- Парсер/аналізатор — Python + `pymavlink` (`DFReader` для `.bin`), `uv` (`pyproject.toml`+`uv.lock`).
- WEB (звіт) — TypeScript/Astro (SSR, `@astrojs/node`) + Tailwind, окремий Docker-контейнер. SSR обов'язковий: список польотів сканується з теки результатів на кожен запит, статичний білд заморозив би його порожнім.
- Парсер і веб на VPS — окремі контейнери, спільна bind-mounted тека результатів (JSON на політ) замість API/БД: парсер пише атомарно (`*.json.tmp` → rename), веб сканує теку на запит.
- Watcher у контейнері парсера спавнить окремий subprocess-воркер на кожен новий файл (`DFReader` CPU-bound і крихкий) — падіння одного парсингу не чіпає прийом інших файлів.
- **Реальний контрактний баг, знайдений живим тестуванням**: `AmplitudeHistogram` падав на реальних даних парсера (`TypeError`, виглядало як "гістограма не показується без reload") — парсер до фіксу рахував гістограму лише для `roll` у пласкій формі `{bin_edges, counts}`, веб очікував по-осьову `{roll: {bins, counts}, pitch: {...}, yaw: {...}}`. Ніякий тест цього не ловив, бо парсерні й веб-тести кожен звіряв дані самі із собою, а не одне з одним. Пофіксовано на боці парсера (`worker.analyze()` рахує гістограму для кожної осі). Урок: раз на якийсь час прогонити реальний `.bin` через увесь ланцюжок.
- **Сторінка `flight/[id].astro` — orchestrator**, а не монолітний блок: `_FlightError.astro`/`_FlightSuccess.astro` колоковані поруч (Astro ігнорує `_`-префіксовані файли в `pages/` при роутингу — стандартний спосіб тримати приватні, невикористовувані-ззовні шматки сторінки поруч, а не в спільному `components/`). Той самий підхід для `VerdictPanel.tsx` → `_MetricsTable.tsx` (компонент, перевикористаний 3 рази ОДНИМ батьком — приватний хелпер, не публічний shared-компонент).
- **Feature-driven організація файлів у веб-сервісі, без `src/components/`.** Компонент, який використовує рівно ОДНА сторінка/батько, живе поруч із ним із `_`-префіксом (`src/pages/_FlightList.tsx` — приватний для `index.astro`; `src/pages/flight/_StickOverlayChart.tsx`, `_AmplitudeHistogram.tsx`, `_VerdictPanel.tsx`, `_RenameableFlightTitle.tsx`, `_MetricsTable.tsx` — приватні для `flight/[id].astro`). Спільна тека компонентів (`src/components/`) з'явиться знову лише тоді, коли реально виникне компонент, перевикористаний ≥2 незалежними сторінками — доти вона оверінженірінг.
- **Метрики на сторінці деталей — 4 окремі таблиці** (roll/pitch/yaw/throttle), не одна з колонкою "вісь". Скалярна `reaction_latency_ms` — окремий блок.
- **Throttle — повноцінна четверта вісь метрик, не лише вхід керування.** Тікет п.3 буквально: "канали RCIN **roll/pitch/throttle/yaw**". До 2026-09-15 throttle читався й нормалізувався (`AXIS_CHANNELS`), але жодна метрика/гістограма/таблиця його не рахували — знайдено повторним звірянням коду з текстом тікета, не тестами (жоден тест не звіряв набір осей із самим тікетом, лише парсер і веб один з одним). `AXIS_CHANNELS`/`AXES` тепер `{roll, pitch, yaw, throttle}`; метрики/гістограма — generic над `flight.sticks`, тож підхопили нову вісь без змін логіки. Графік стіків-поверх-attitude свідомо НЕ показує throttle (у attitude немає throttle-еквіваленту для порівняння) — це відповідає лише "стіки поверх attitude", не п.3.
- **Крок слайдера порогів = 1 для дискретних метрик** (`corrections_per_min`, `reaction_latency_ms` — події/хв, мс), `"any"` для справді неперервних.
- **Reset-view + зум колесом на графіках** (`lib/chartZoom.ts`, спільний для двох uPlot-компонентів) — uPlot сам не дає кнопки "скинути" після drag-zoom.
- **Список польотів — React-острів (`FlightList.tsx`, `client:load`) з клієнтським поллінгом**, не htmx. Було: `hx-trigger="every 1s"` + окремий partial-роут. Замінено, коли з'ясувалось, що для того самого списку вже потрібен React-стейт (бейджі вердикту, перейменування) — тримати паралельно htmx-DOM-свапи й React-стейт для сусідніх елементів однієї картки виявилось зайвою другою моделлю клієнтської логіки без реальної вигоди. Поллінг тепер — `fetch('/api/flights')` (JSON-роут, той самий `listFlights()`) у `window.setInterval`, раз на секунду.
- **Перейменування польотів у UI** — суто клієнтське (`src/lib/localName.ts` + React-стейт у `FlightList.tsx`/`RenameableFlightTitle.tsx`, `localStorage`, без сервера/БД), приватне для одного браузера. Було окремим vanilla-DOM `<script>` (TS-файл у `src/scripts/`, бандлений Astro/Vite як звичайний файл проєкту) — після переходу списку на React це стало просто стейтом компонента, без ручної DOM-синхронізації.

**Тестування (обов'язкові правила)**
- Тести пишуться для **всіх** компонентів: парсер, веб-аналізатор, keyboard-адаптер.
- **AAA**: кожен тест поділений на Arrange / Act / Assert, у цьому порядку, з коментарями-маркерами.
- **Жодних управляючих конструкцій у тілі тесту** — ніяких `if`/`for`/`while`/`try`/`switch`, тернарників і `.forEach` з логікою. Кілька наборів даних — параметризацією (`pytest.mark.parametrize`, `test.each`), а не циклом усередині тесту.
- Перед написанням тестів — спочатку **виписати сценарії та граничні значення**, потім кодувати.
- Один тест = одне твердження про поведінку; назва описує сценарій, не метод.
- E2E для вебу — **Playwright**.
- TypeScript — додатково **ESLint** (+ типи в CI-команді `npm run lint`).
- Python — **повністю типізований** (анотації на всіх публічних функціях, методах і полях), перевірка **mypy** у strict-режимі; `mypy` — частина dev-залежностей і команди перевірки, не опційний крок.

**Розгортання**
- docker-compose (parser, web, caddy) — однаковий локально й на VPS, різниться лише конфіг/env (WireGuard-peer, домен).
- **Розгортання на VPS — shell (`vps/provision.sh`), не Ansible.** Тікет прямо дозволяє "docker-compose / Ansible / shell — на вибір"; для одного VPS і одноразового прогону (без continuous config drift, без десятків хостів) Ansible-плейбуки — оверінженірінг: цінність Ansible (ідемпотентність, керування станом багатьох хостів) тут не окупається, а рев'юєру довелось би читати YAML/Jinja замість лінійного bash. Критерії приймання тікета оцінюють результат ("тунель піднятий", "логи потрапляють", "звіт відкривається"), не інструмент.
- **Два провіжен-скрипти, однакова назва файлу з обох боків: `local/provision.sh` (SITL-хост) і `vps/provision.sh` (VPS).** Той самий патерн, той самий файл — одноразовий, sudo, ідемпотентний, запускається з клона репозиторія на своєму хості (не з робочої машини). Раніше файл на SITL-боці звався `prereqs.sh` — перейменовано, щоб симетрія в назві сама documentувала симетрію ролі, без потреби пам'ятати дві різні назви для двох половинок одної процедури.
- **`vps/deploy.sh` видалено — злито в `vps/provision.sh`.** Розділення "зібрати образи (десь) → перенести → розгорнути (десь інде)" мало сенс, коли образ збирався на Mac (arm64) під ціль VPS (amd64) і мусив кудись переноситись offline-tar'ом. Коли `provision.sh` сам запускається З КЛОНА РЕПОЗИТОРІЯ НА САМОМУ VPS (а не з робочої машини) — VPS уже нативно `amd64`, тож жодного крос-білду/перенесення не треба: `docker compose build && up -d` прямо там, де контейнер і буде жити. Один крок замість двох, без втрати ідемпотентності (compose build/up без змін — no-op).
- **Живцем перевірено на реальному VPS (`root@1.zdc.space`, Ubuntu `noble`/`x86_64`): вихід в інтернет є** (apt-репозиторії `mirrors.digitalocean.com`/`security.ubuntu.com` доступні, `git` уже встановлений — `2.43.0`). Попереднє припущення "вважати, що нема" було обережним, не підтвердженим — знято.
- **Self-signed сертифікат за замовчуванням (переглянуте рішення, 2026-09-17).** Раніше свідомо відмовились від self-signed ("мовчазний фолбек авансом без реальних даних") і Caddy був лише HTTP (`:80`). Але критерій приймання тікета буквально вимагає "звіт відкривається по HTTPS" — а до реального домену/сертифіката від замовника (Сергій, за запитом) невідомо коли дійде черга, тож замовника вирішено не чекати. `vps/provision.sh` тепер сам генерує self-signed (`openssl req -x509`, `CN`/`SAN` = публічний IP чи `VPS_PUBLIC_HOST`) у `/srv/app/certs/{server.crt,server.key}` **лише якщо там ще нічого нема** — реальний сертифікат замовника, покладений під тими самими іменами в ту саму теку, підміняє self-signed без зміни `Caddyfile`/скрипта (повторний прогін `provision.sh` бачить наявні файли й не чіпає їх). `Caddyfile` тепер обслуговує і `:80`, і `:443` (`tls /certs/server.crt /certs/server.key`); `ufw` відкриває і 443. Браузер показуватиме попередження про self-signed, доки не буде реального сертифіката — очікувано, не баг.
- **`vps/provision.sh` живцем перевірено на реальному VPS** (до попереднього рефакторингу, ще з `deploy.sh` окремо) — Docker Engine (apt, офіційний репозиторій), `ufw`, WireGuard-сервер піднялись без правок. Ідемпотентність підтверджена практично: прогнано з тимчасовим `CLIENT_WG_PUBKEY` (SITL-хост ще не був доступний), потім планувалось перезапустити з реальним — `wg-quick@wg0` `restart`, не `start`, саме для цього. Змінений (злитий з `deploy.sh`, без 443) варіант — ще не перевірений живцем на реальному VPS, лише на `VPS-test`.
- Dockerfile'и (parser, web) — multi-stage, щоб фінальний образ був без білд-залежностей (uv/npm), тільки рантайм-артефакти.
- **WireGuard — окремі симетричні скрипти (`local/setup-wireguard.sh` + `vps/setup-wireguard.sh`), не частина `provision.sh` жодного з боків.** Обидва `provision.sh` не займаються WireGuard-конфігом взагалі (лише ставлять пакет `wireguard-tools`) — прибрано `CLIENT_WG_PUBKEY`/`SERVER_WG_PUBKEY`/`VPS_ENDPOINT` як їхні параметри.
  - **Два режими, а не один.** Спершу був лише "автоматичний" (SSH з SITL-хоста на VPS завжди є) — виявилось хибним припущенням: тунель сам є прямим критерієм приймання тікета, тож має підійматись і тоді, коли SSH між хостами немає (інша мережа, фаєрвол, VPS адмінить хтось інший — цей сценарій не можна відкидати як неможливий лише тому, що в нашому випадку SSH є). Тому `vps/setup-wireguard.sh` — самостійний файл, який можна запустити вручну на VPS з `CLIENT_WG_PUBKEY=...` (друкує публічний ключ сервера окремим останнім рядком stdout, решта виводу — в stderr, саме щоб цей рядок можна було забрати командною підстановкою); `local/setup-wireguard.sh` так само вручну, з `SERVER_WG_PUBKEY`+`VPS_ENDPOINT`.
  - **Автоматичний режим — не окрема логіка, а той самий `vps/setup-wireguard.sh`, викликаний по SSH.** Коли `local/setup-wireguard.sh` отримує `VPS_HOST`, він не дублює серверну частину інлайн-бешем (як було раніше) — просто виконує `ssh $VPS_HOST '.../vps/setup-wireguard.sh'` з клона репозиторія, що вже є на VPS (той самий клон, з якого запускали `vps/provision.sh`), і забирає з stdout той самий публічний ключ сервера. Одна точка правди для серверної логіки, а не дві копії (локальна інлайн-версія + файл).
- Порядок: повністю зібрати й перевірити локально (SITL нативно у VM, parser, web, тестовий WireGuard між UTM-VM і локальним docker compose) → тоді `vps/provision.sh` на реальний VPS/DNS, фінальний прогін строго за README.
- **Тестовий WireGuard — перевірено двома docker-мережами, не двома VM.** Другої фізичної VM не було під рукою, план явно допускає цю альтернативу ("дві Ubuntu-VM (або два docker-нетворки)"). Дві ізольовані мережі без спільного docker-network (UDP сервера опубліковано на хості, як публічний IP на реальному VPS) — інакше тест нічого не довів би: без реальної ізоляції rsync пройшов би й напряму, без тунелю. Результат: handshake, ping крізь `10.10.0.0/24`, `rsync` реального `.BIN` (11 МБ) побайтово ідентичним, `parser.worker` на ньому відпрацював без помилок. Конфіги пишуть самі скрипти (`vps/setup-wireguard.sh` + `local/setup-wireguard.sh`), не приклади вручну.
- **SITL не контейнеризується.** Тікет дослівно: "у віртуальній машині або на bare-metal (технологію обираєш сам)" — Docker як варіант не згаданий, а VM (UTM Ubuntu) уже дає ізоляцію, другий шар нічого не додає. SITL піднімається нативно через `sim_vehicle.py` прямо в Ubuntu VM/bare-metal; GCS/візуалізатор (MAVProxy) і keyboard-adapter — там само на хості, без проброшених портів контейнера. Контейнеризація лишається лише там, де тікет її фактично вимагає — `parser`/`web` на VPS.
- **Візуалізація — MAVProxy** (`--master=tcp:127.0.0.1:5760 --map --console`): закриває і роль GCS, і візуалізацію. Тікет 3D **не вимагає** («на твій розсуд: FlightGear, Mission Planner/QGC з картою чи інше»), тож мапи достатньо. Відпадають QGC/AppImage/`libfuse2`, FlightGear і вимога до 3D-прискорення у VM. FlightGear — опційно, лише заради ефектнішого запису.
- Підготовка хоста (пакети, libfuse2 для QGC) — `docs/host-prerequisites.md`, чернетка для README.
- **`local/provision.sh` (одноразовий, sudo) + `local/run-sitl.sh` (повторюваний, без sudo)** — той самий поділ, що на VPS-боці (`vps/provision.sh`, тепер і назвою файлу однаковий). `provision.sh` клонує **офіційний апстрім** ArduPilot (не форк) у гітignored `.sitl/` (як `assets/`/`data/`/`worktrees/`), виставляє пінований тег, ставить `install-prereqs-ubuntu.sh` + додаткове (`wireguard-tools`/`rsync`/`git-lfs`, групу `input`, `evdev`) — одним `sudo`-запитом (`sudo -v` на старті). `run-sitl.sh` піднімає SITL+MAVProxy, `Ctrl+C` зупиняє їх разом. Замінив окремий `tools/setup-host.sh` — його вміст мігрував у `provision.sh`, не зник. (Файл перейменовано з `prereqs.sh` пізніше — див. розділ «Розгортання».)
  - **Shallow-клон (`--depth 1 --branch <тег> --shallow-submodules`), не повний.** ArduPilot upstream — велика історія (десятки тисяч комітів, багато релізних тегів і форків) і купа submodule-ів (mavlink, EKF, gtest тощо); для збірки SITL з конкретного пінованого тега повна історія не потрібна взагалі. Ідемпотентний повторний прогін з ІНШИМ `ARDUPILOT_TAG` (переліт тега) робить додатковий `git fetch --depth 1 origin tag <новий>` замість припущення, що тег уже десь у локальній історії (у shallow-клоні його там і нема).
  - **Живцем виявлено на `SITL-test`: MAVProxy/pymavlink стоять у venv (`~/venv-ardupilot`), не системно/`--user`.** `install-prereqs-ubuntu.sh` сам робить `python3 -m venv --system-site-packages $HOME/venv-ardupilot` і НЕ дописує `source .../activate` у `.bashrc` за замовчуванням (інтерактивний "Make ArduPilot venv default? [N/y]", non-interactive `-y`-прогін лишає N). На Ubuntu 24.04 системного `pip3` навіть немає (PEP 668) — `prereqs.sh` ставить `evdev` через `$HOME/venv-ardupilot/bin/pip3` явно, з `--user`-фолбеком, якщо venv не знайдено; `run-sitl.sh` сам джерелить `venv-ardupilot/bin/activate` і додає `Tools/autotest` у `PATH` (`sim_vehicle.py` там, а не встановлений як команда). Без цього: `--load-module keyboard_adapter`/`evdev` падали б на `ImportError`, а `sim_vehicle.py` — на `command not found`.
  - **Живцем виявлено: `install-prereqs-ubuntu.sh` завжди робить `pip install -U wxpython` і компілює з джерела** (20-40+ хв на 4 vCPU arm64) — незалежно від того, чи є apt-пакет `python3-wxgtk4.0`. Не наша проблема зараз: `horizon` (нижче) прибрано, wxPython нам більше не потрібен узагалі.
  - **Живцем виявлено: свіжий Ubuntu Desktop install не має `git`** (`prereqs.sh` падав на `git: command not found` до `apt install git` вручну) — і VM-клок може бути суттєво розсинхронізований після довгого simulate/pause у UTM (`apt-get update` падав на "Release file... is not valid yet"), що ламає `apt` доти, доки не форснути `timedatectl set-ntp false && set-ntp true`.
  - **Відхилено: форк ArduPilot як git submodule на піновому тезі.** Ідея сама по собі дешева (форк не потребує підтримки апстріму), але прямо конфліктує з тікетом: "Що здати" вимагає README+скрипти розгортання **в репозиторії**, критерій приймання — "стенд відтворюється за README без пояснень". Винесення README/SITL-інструкцій в окремий репозиторій (форк) означало б, що репозиторій, який отримає рев'юєр, формально не містить інструкції з відтворення стенду.
- **keyboard-adapter — MAVProxy-модуль (`init()` у `local/keyboard_adapter/src/keyboard_adapter/__init__.py`), не окремий процес.** Спершу (перша ітерація) винесли в окремий процес із власним UDP-конектом (`cli.py`) саме через таймінг 20 Гц (окремий `Clock.sleep()`) і розв'язаність життєвих циклів (GCS можна перезапустити без втрати керування) — але це виявилось невиправданим ускладненням ("сайдкар", не ідіоматично для MAVProxy: map/console/antenna-tracker так само розширюють MAVProxy модулями). Тайминг-заперечення знялось, щойно з'ясувалось, що модуль може крутити той самий `run_loop` у ВЛАСНОМУ треді (`keyboard_adapter.mavproxy_glue.start_control_thread`), не в single-threaded idle-loop MAVProxy — ділити такт нема з чим. Лишається один реальний, свідомо прийнятий компроміс: **падіння самого процесу MAVProxy тепер тягне за собою й керування** (раніше — ні, окремий процес пережив би рестарт GCS). Пом'якшено настільки, наскільки дозволяє архітектура MAVProxy: падіння ОКРЕМОГО модуля (map/console) інших модулів не валить — клавіатурний тред продовжує слати `MANUAL_CONTROL` "наосліп" (без HUD/мапи), доки живий сам процес MAVProxy; лише повний крах процесу MAVProxy зупиняє й керування. `loop.py`/`axes.py` (тестоване ядро) не змінились; `mavproxy_glue.py` — нова тестована обв'язка (адаптація `self.master`, кооперативна зупинка через `run_loop`'s `should_stop`).
  - **Живцем виявлено (перша спроба помилялась): MAVProxy НЕ шукає сторонні модулі за файлом `mavproxy_<name>.py` на `PYTHONPATH`.** Реальний код `load_module()` (`MAVProxy/mavproxy.py`) пробує `MAVProxy.modules.mavproxy_<name>` (лише для модулів усередині самого пакета MAVProxy), а фолбек — імпорт голого `<name>` (наш випадок, `--load-module keyboard_adapter` → `import keyboard_adapter`). Перший варіант (окремий top-level файл `mavproxy_keyboard_adapter.py` поряд із пакетом) падав живцем: `import keyboard_adapter` знаходив НАШ ЖЕ ПАКЕТ (той самий `keyboard_adapter/`, потрібний для `from keyboard_adapter.evdev_source import ...`), не окремий файл — `ERROR ... module 'keyboard_adapter' has no attribute 'init'`. Виправлено: `init(mpstate)` (лінива імпортація `MAVProxy.modules.lib.mp_module`, локально визначений `MPModule`-підклас усередині функції — щоб решта пакета лишалась імпортовною й тестовною без MAVProxy) живе прямо в `keyboard_adapter/__init__.py`; окремий шим-файл видалено.
  - **Живцем виявлено: запуск `sim_vehicle.py`/MAVProxy без реального терміналу (лише через `ssh` без pty) валить увесь процес одразу.** MAVProxy читає команди з `MAV>`-прompt через `input_loop()` у головному потоці — на EOF stdin (наш перший тест: `ssh` без `-tt`, stdin не підключений до терміналу) вона миттєво завершує головний цикл і вивантажує геть усі модулі, включно з щойно завантаженим `keyboard_adapter`. Це не бага run-sitl.sh — реальний користувач запускає його зі свого термінала в GUI-сесії VM, де stdin є нормальним TTY; проблема була суто в моєму способі тестування (виправлено використанням `ssh -tt`).
  - **Відкинуто заразом: два клавіатурних бекенди (`pynput`+`evdev`).** Раніше `pynput` (X11 Xorg) був дефолтом, `evdev` — альтернативою для Wayland через `--input-backend`. Оскільки продакшн-шлях тепер один (MAVProxy-модуль, не вибір користувача під час запуску) і `evdev` однаково працює на Xorg і Wayland — тримати другий бекенд лише заради Xorg-сесії сенсу нема: зайва гілка коду, зайвий вибір сесії логіну. `keyboard.py` (pynput) видалено, `evdev` — єдиний бекенд.
  - **Тротл на `Up`/`Down`, не на `Shift`/`Ctrl`.** `evdev` читає клавіші сиро, незалежно від фокуса вікна (сама причина вибору `evdev` — Wayland) — тож `Shift`/`Ctrl` як типові модифікатори під час друку команд у `MAV>` (велика буква режиму, `Ctrl+C`) заодно рухали б тротл. `Up`/`Down` у тексті команд не з'являються — конфлікту нема без жодної toggle-логіки чи детекту фокуса (перевірено живцем через реальний код MAVProxy `input_loop()`/`rline.py`: модулі не отримують жодної події "користувач друкує", лише готову строку після Enter — детектити фокус консолі з рівня модуля неможливо в принципі).
  - **`keyboard_adapter` вимагає явного `kb on`, а не лише FBWA+armed.** `mavproxy_glue.should_control(flightmode, armed, kb_enabled)` — три умови одночасно, не дві. `FBWA + armed` самі по собі можуть настати ще на землі чи випадково під час рулювання; третя умова (`kb on`/`kb off`, MAVProxy-команда, дефолт — вимкнено) — свідомий запобіжник: пілот сам включає керування, воно не підхоплюється автоматично за фактом режиму/арму. `disarm`, вихід із FBWA чи `kb off` — будь-яка з трьох умов, що стала хибною, однаково зупиняє тред.
- **`speech`/`graph` — відхилено (спробували й прибрали), `horizon` — повернуто.** Ідея — живий фідбек під час клавіатурного пілотування (озвучка режиму/arm/failsafe, графік attitude, намальований авіагоризонт), усі три реально існують і вантажились живцем без помилок. Спершу прибрано всі три за прямим запитом — тримати лише `keyboard_adapter`, без зайвого. Пізніше `horizon` повернуто окремим запитом (`speech`/`graph` лишаються прибраними): `run-sitl.sh` вантажить `--load-module keyboard_adapter --load-module horizon`. `horizon` тягне wxPython (`python3-wxgtk4.0`), але `install-prereqs-ubuntu.sh` і так компілює свою копію wxPython з джерела (20-40+ хв) незалежно від apt-пакета — повернення `horizon` не додає часу на встановлення понад те, що вже витрачається на `prereqs.sh`.
- Логи доставляються `rsync`/`scp` через WireGuard у watched-теку парсера, не жива стрім-передача.
- **Доставка логів на VPS — автоматична, не ручна команда (`local/push-logs.sh`).** Критерій приймання тікета буквально: "Логи з SITL автоматично потрапляють на VPS і з'являються у списку" — `make fetch-logs` (rsync з VM на Mac у `data/inbox`) закриває лише dev-зручність локальної перевірки пайплайна, НЕ цей критерій (інший напрямок, інша мета). `local/run-sitl.sh` сам запускає `push-logs.sh` у фоні (вбиває його разом із собою через `trap ... EXIT`): `inotifywait -e close_write` на `.sitl/ArduPlane/logs/` — щойно ArduPilot закриває `.BIN` (кінець польоту/дизарм), файл негайно `rsync`иться на VPS через WireGuard (`10.10.0.1`, конфіг пише `local/setup-wireguard.sh`); `.tlog` — окремо, періодично (весь час відкритий протягом сесії, "закриття" дочекатись не можна). Невдалий `rsync` (тунель/VPS ще не піднятий) лише логується, не валить спостереження. **[не перевірено на реальному VPS]** — сама механіка (`inotifywait`/`rsync` викликаються правильно, чистий `kill` без процесів-сиріток) перевірена локально фейковими `inotifywait`/`rsync`; живий прогін через реальний тунель до реального VPS — після `vps/provision.sh`.
- Відео польоту для здачі — поза VPS/сервісом (репозиторій/git-lfs або посилання в README).

**Керування (замість джойстика)**
- Клавіатура погоджена замовником напряму.
- `pymavlink`, `MANUAL_CONTROL` (осі x/y/z/r), 20 Гц, MAVProxy-модуль (див. вище). Клавіатурний бекенд — лише `evdev` (kernel `/dev/input`, однаково на Xorg і Wayland — X11 global-grab (`pynput`) не отримав би подій на Wayland узагалі, архітектурне рішення Wayland, не баг бібліотеки; другий бекенд для Xorg-варіанту не виправданий, коли шлях запуску один). `evdev` — лінукс-специфічний, env-маркер у `pyproject.toml` не дає `uv sync` ставити його на macOS (стенд там і не запускається).
- Обов'язково spring-return: плавне наростання/повернення до нейтралі — інакше метрики амплітуди/jerk спотворяться.
- Обґрунтування заміни джойстика зафіксувати в README.

**Політ і докази для здачі**
- Синтетичні польоти — ок для тестування пайплайну метрик; для обов'язкових 3+ польотів у здачі потрібен реальний ручний ввід (клавіатура).
- Основний доказ — екранний запис (вікно візуалізації + web-звіт в одному кадрі); опційно відео телефоном рук на клавіатурі.

**Good/bad шаблони**
- Надаються замовником разом із VPS-доступом, з інтернету не брати — оцінка прив'язана саме до них.
- Три шари: (1) парсер рахує лише сирі детерміновані метрики з п.3 тікета (корекції/хв, амплітуда/різкість, % часу в осциляціях, затримка реакції); (2) веб-сторінка польоту рендерить графік стіків поверх attitude, гістограму амплітуд і зведені числа з (1); (3) вердикт за шаблонами.
- **Вердикт — if/else за наданими шаблонами, без LLM.** Рішення прийняте: жодної залежності від зовнішнього API/ключа на проді, рев'юєр піднімає стенд без ключів. LLM не використовувати.

**Програма польоту**
- Набір льотних вправ/маневрів (зліт, розвороти, витримка курсу тощо), які підкаже замовник — інструкція "що робити стіками", не waypoint-файл. У логах не зберігається окремо (немає MISSION-записів при ручному польоті), маршрут можна лише реконструювати з POS/ATT/GPS постфактум.
- Використовувати одну й ту саму програму для всіх 3+ залікових польотів — інакше метрики різних польотів непорівнянні.
- До отримання офіційної — `assets/demo-flight-task.md` (реконструйовано з `flight-01_2026-09-11.bin`), тимчасовий сурогат лише для розробки/тестування пайплайну. Замінити посиланням на офіційну.

**Алгоритм оцінки (вердикт)**
- Опис і формат конфігу порогів — `docs/scoring-algorithm.md`. Пороги там зараз placeholder (з демо-польоту) — замінити на реальні одразу після отримання good/bad-шаблонів, без зміни коду (лише конфіг).
- Пороги (`good_max`/`warn_max`) — **налаштовувані на клієнті** під час перегляду звіту (слайдери/інпути в UI), не захардкоджені на сервері. Сервер віддає лише метрики + дефолтні пороги; категоризацію (if/else) рахує браузер, миттєво, без запиту на сервер.
- **Категорія `crashed` — переважає над `good`/`warning`/`bad`.** Парсер (`worker.analyze`) рахує `crashed: bool` = `STAT.Crash` (вбудований детектор ArduPilot, `Plane::crash_detection_update()`) **АБО** власна евристика (`metrics.detect_crash_heuristic`): хвіст логу (3с) на низькій висоті (`POS.RelHomeAlt` ≤ 2м) з екстремальним креном/тангажем (> 60°). `STAT.Crash` сам по собі **не годиться як єдине джерело** — перевірено через DeepWiki по `ArduPilot/ardupilot`: `crash_detection_update()` активний лише в `AUTO`, а весь профіль здачі — ручні `MANUAL`/`FBWA`, де він не спрацює навіть при реальному падінні. Обидва сигнали if/else, задокументовані, без ML.
- **Дискретне форматування у UI.** `corrections_per_min`/`reaction_latency_ms` дискретні за суттю (події/хв, мс) — округлюються до цілого у відображенні (`lib/verdict.ts: formatMetricValue`), а не показуються з довільним хвостом десяткових знаків парсера. `mean_amplitude`/`mean_jerk`/`oscillation_time_pct` справді неперервні, лишаються без змін. Окремо — колонка "кількість" (`correctionsCount`) відновлює цілий лічильник корекцій точним зворотним обчисленням із `corrections_per_min * analyzed_duration_s / 60` (парсер сирий лічильник у JSON не віддає).
- **Список польотів показує бейджі вердикту одразу** (`FlightList.astro`), не лише тривалість — рахує `computeVerdict` + `withCrashOverride` синхронно на сервері (чиста функція, безпечно і в SSR, і в браузері).
