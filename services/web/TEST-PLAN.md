## 1. Юніт-тести `src/lib/verdict.ts` (vitest)

Чиста функція `computeVerdict(metrics, thresholds) => {verdict, reasons}`.
Порівняння за `docs/scoring-algorithm.md`:
`value <= good_max` → `good`; `good_max < value <= warn_max` → `warning`; `value > warn_max` → `bad`.
Загальний вердикт — **найгірша** категорія (worst-case).

### 1.1 Категоризація одного значення (межі)

Базовий поріг для таблиці: `good_max = 6`, `warn_max = 12`.

| # | value | очікувана категорія | чому це межа |
|---|-------|---------------------|--------------|
| T1 | `0` | `good` | значно нижче good_max |
| T2 | `5.999` | `good` | трохи нижче good_max |
| T3 | **`6`** (рівно `good_max`) | `good` | порівняння `<=`, не `<` — класична off-by-one |
| T4 | `6.001` | `warning` | перша точка за good_max |
| T5 | `11.999` | `warning` | трохи нижче warn_max |
| T6 | **`12`** (рівно `warn_max`) | `warning` | `<= warn_max` → warning, НЕ bad |
| T7 | `12.001` | `bad` | перша точка за warn_max |
| T8 | `1000` | `bad` | значно вище |
| T9 | `-5` | `good` | від'ємне (теоретично неможливе) не має ламати логіку |

### 1.2 Worst-case агрегація

- `V1` усі осі й метрики `good` → загальний вердикт `good`.
- `V2` одна вісь `warning` серед `good` → загальний `warning` (не «розчиняється»).
- `V3` одна вісь `bad` серед `good` → загальний `bad`.
- `V4` є і `warning`, і `bad` → загальний `bad` (bad важчий за warning).
- `V5` порядок метрик у вхідному об'єкті не впливає на результат (той самий набір,
  інший порядок ключів → той самий вердикт).

### 1.3 `reasons`

- `R1` при повністю хорошому польоті `reasons` НЕ містить жодного запису з категорією `bad`.
- `R2` `reasons` містить запис `{metric, axis, value, category}` саме для тієї осі,
  що вийшла за поріг (перевірка адресності: `mean_jerk`/`roll`).
- `R3` скалярна метрика `reaction_latency_ms` потрапляє в `reasons` з `axis === null`
  (немає розбивки по осях).
- `R4` кожна вісь кожної метрики дає рівно один запис у `reasons` (кількість = 3 осі × 4 метрики + 1 скаляр = 13).

### 1.4 Деградація вхідних даних (не має кидати виняток)

- `E1` метрика присутня в `metrics`, але **відсутня в `thresholds`** → метрика ігнорується,
  вердикт рахується з решти (не `bad`, не throw).
- `E2` метрика присутня в `thresholds`, але відсутня в `metrics` → ігнорується.
- `E3` `NaN` як значення метрики → категорія `unknown`, не впливає на worst-case.
- `E4` `Infinity` → `bad` (більше за будь-який warn_max).
- `E5` `-Infinity` → `good`.
- `E6` `null`/`undefined` як значення осі → `unknown`, без винятку.
- `E7` **порожній набір метрик** (`{}`) → вердикт `good`, `reasons` порожній (нічого не порушено).
- `E8` порожні пороги (`{}`) при непорожніх метриках → вердикт `good`, `reasons` порожній.
- `E9` `warn_max < good_max` (зіпсований конфіг) → функція не кидає виняток
  (детермінований результат: перемагає перша умова `<= good_max`).

### 1.5 Чистота

- `P1` виклик функції не мутує переданий об'єкт `metrics` (deep-equal до і після).
- `P2` два виклики з тими самими аргументами дають однаковий результат (детермінізм).

## 2. Юніт-тести `src/lib/results.ts` (vitest, tmp-тека)

- `L1` валідний id (`flight-01`, `a_B-9`) проходить регулярку `/^[A-Za-z0-9_-]+$/`.
- `L2` id з `..`/`/`/крапкою (`../etc/passwd`, `a.b`, `a/b`, порожній рядок) — **не** проходить.
- `L3` `listFlights` на порожній теці → порожній масив.
- `L4` `listFlights` ігнорує файли, що не `.json` (напр. `.json.tmp` від атомарного запису парсера).
- `L5` `listFlights` повертає шапку без `series` (перевірка, що важкі дані не потрапляють у список).
- `L6` `listFlights` позначає `<id>.error.json` як `status: 'error'`.
- `L7` `readFlight` для неіснуючого id → `null`.
- `L8` `readFlight` для невалідного id → `null` (не читає ФС взагалі).

## 3. E2E (Playwright, реальний SSR-сервер + tmp `RESULTS_DIR`)

Сервер піднімається з `RESULTS_DIR`, що вказує на тимчасову теку з фікстурами
(`flight-good.json`, `flight-bad.json`, `flight-broken.error.json`).

### 3.1 Список польотів

- `A1` порожня тека результатів → сторінка віддає 200 і показує повідомлення «немає польотів»
  (не 500, не порожній екран).
- `A2` один політ → у списку рівно одне посилання на політ.
- `A3` кілька польотів → у списку всі вони (перевірка кількості карток).
- `A4` політ з `.error.json` показується у списку як помилка (бейдж/текст «помилка»), а не зникає.

### 3.2 Сторінка польоту

- `B1` існуючий id → 200 і заголовок містить `flight_id`.
- `B2` **невалідний id** в URL (`../secret`, `flight%2F..`) → 404.
- `B3` **неіснуючий** валідний id (`flight-zzz`) → 404.
- `B4` `.error.json`-політ → сторінка рендериться зі станом помилки (текст помилки видно),
  HTTP 200, без 500.
- `B5` графік стіків (`StickOverlayChart`) рендериться — у контейнері з'являється `canvas`.
- `B6` гістограма амплітуд рендериться — у контейнері з'являється `canvas`.

### 3.3 Інтерактив `VerdictPanel`

- `C1` при дефолтних порогах політ `flight-good` показує вердикт `good`.
- `C2` при дефолтних порогах політ `flight-bad` показує вердикт `bad`.
- `C3` **зміна слайдера порогу змінює вердикт без перезавантаження сторінки**:
  на `flight-good` зменшуємо `good_max` нижче фактичного значення → вердикт стає гіршим,
  і при цьому лічильник навігацій сторінки не змінився (перевірка «без reload»).
- `C4` повернення слайдера у вихідне значення повертає початковий вердикт (оборотність).
- `C5` панель вердикту гідратується як острів (`client:load`): кнопка/слайдер реагує на ввід,
  тобто JS активний, а не лише SSR-розмітка.

### 3.4 React-поллінг списку польотів (`tests/e2e/polling.spec.ts`)

Індексна сторінка оновлює список раз на секунду без повного перезавантаження —
nice-to-have замість push/SSE (поллінг стійкіший: не треба тримати з'єднання живим і
переперепідключати). **Було htmx (`hx-trigger="every 1s"` + outerHTML-свап партіалу),
замінено на React**: `FlightList.tsx` (`client:load`) сам робить `fetch('/api/flights')`
кожну секунду (`window.setInterval`) і оновлює власний `useState`, без htmx і без
окремого partial-роуту (JSON API — `src/pages/api/flights.ts`). Причина заміни: коли в
проєкті вже є React-острови (`VerdictPanel`), тримати паралельно й htmx для одного
компонента — зайва друга модель клієнтського стану; React until-then і так найкраще
підходить для того самого списку, де вже рахується `verdictBadge`/`crashed`.
Окремий сервер/тека `live` (порожня на старті) — `populated` спільна й читається
паралельно іншими тестами, писати в неї під час прогону не можна.

- `D1` порожня `live`-тека на старті → лише порожній стан.
- `D2` файл, покладений у теку ПІСЛЯ відкриття сторінки, з'являється в списку сам,
  без `page.reload()` — головний сценарій.
- `D3` **поллінг триває довше одного тика**: другий файл, покладений після того, як
  перший уже з'явився, теж з'являється сам — перевіряє, що `setInterval` не
  зупиняється після першого оновлення (аналог колишньої htmx-перевірки "не зникає
  після свапу", адаптований під React: тут немає обгортки з атрибутами, які могли б
  зникнути, натомість перевіряється сам факт повторюваності поллінгу).

Тести файлу виконуються послідовно (`test.describe.configure({ mode: 'serial' })'`),
бо кожен додає файл поверх стану, залишеного попереднім, — паралельний прогін у межах
одного файла дав би недетермінований порядок і хиткі лічильники.

**Перейменування тепер теж React** (`FlightList.tsx`/`RenameableFlightTitle.tsx`,
`src/lib/localName.ts`) — той самий `localStorage`, але як стан компонента замість
DOM-запитів після `htmx:afterSwap`; на детальній сторінці — окремий маленький острів
`RenameableFlightTitle`, без поллінгу.

## 3.5. Дискретна кількість корекцій (`correctionsCount`, колонка "кількість")

Парсер віддає лише `corrections_per_min` (похідну швидкість) — сирий лічильник
переходів через deadband у вихідний JSON не потрапляє. Клієнт (`lib/verdict.ts`)
відновлює цілу кількість точним зворотним обчисленням:
`count = round(corrections_per_min * analyzed_duration_s / 60)` — точно, не
оцінка, бо саме так парсер і рахував швидкість.

- unit (`verdict.test.ts`): типовий випадок (звірено з реальним польотом
  `00000004`), точне ділення без округлення, нульова швидкість,
  `analyzedDurationS <= 0` → нулі на всіх осях.
- e2e (`verdict-panel.spec.ts`): колонка "кількість" у `reasons-table` показує
  правильне число для `corrections_per_min` на кожній осі; для інших метрик
  (`mean_amplitude` тощо) — порожній прочерк (кількість там немістить сенсу,
  це не рахунок подій).

**Форматування значень (`formatMetricValue`)** — окремо від "кількість":
`corrections_per_min` і `reaction_latency_ms` дискретні за суттю (події/хв,
мс), тож у колонці "значення" округлюються до цілого (`4.1796` → `4`), а не
показуються з довільним хвостом десяткових, як їх віддає парсер. Решта
метрик (`mean_amplitude`, `mean_jerk`, `oscillation_time_pct`) справді
неперервні — лишаються без змін.

## 3.6. Перейменування польотів (`rename.spec.ts`)

Суто клієнтська фіча (`src/lib/localName.ts` + стан React-компонентів
`FlightList.tsx`/`RenameableFlightTitle.tsx`, `localStorage`, без сервера/БД)
— кнопка ✎ на картці списку і на заголовку сторінки деталей, `window.prompt()`
для вводу нової назви. Раніше — окремий vanilla-DOM `<script>`, що вручну
перезаписував текст і перепідписувався на `htmx:afterSwap`; після переходу
списку на React-поллінг це стало просто React-стейтом (`names`), простіше й
без ручної синхронізації з DOM.

| Сценарій | Очікування |
|---|---|
| кнопка перейменування присутня на сторінці деталей / на кожній картці списку | видима, `data-testid="rename-flight"` |
| підтвердження діалогу з новою назвою → перезавантаження сторінки | нова назва лишається (і на деталях, і на картці списку) |
| скасування діалогу (`dismiss`) | назва не змінюється, лишається `flight_id` |
| підтвердження діалогу з порожнім рядком | відображення повертається до `flight_id` (порожнє ім'я прибирає override) |

Не тестується: синхронізація між різними браузерами/глядачами — `localStorage`
свідомо приватний для одного браузера, це узгоджене обмеження, не недогляд.

## 3.7. `crashed` переважає числові пороги (`withCrashOverride`)

Парсер віддає `crashed: bool` (`STAT.Crash` АБО евристика по хвосту логу —
див. `services/parser/TEST-PLAN.md` §10.10). Фізичний інцидент має бути
показаний як гірший за будь-яку числову категорію — навіть якщо всі метрики
"good", `crashed=true` дає вердикт `crashed`, найгіршу з чотирьох категорій
(`good < warning < bad < crashed`).

- unit (`verdict.test.ts`): `withCrashOverride` для всіх комбінацій
  вердикт×crashed.
- e2e (`verdict-panel.spec.ts`, фікстура `flight-crashed` — усі метрики good,
  `crashed: true`): сторінка деталей і картка в списку обидві показують
  `data-verdict="crashed"`, попри "хороші" числа.
- Колір бейджа `crashed` — окремий, інтенсивніший за `bad` (не той самий
  rose/red — щоб на швидкий погляд не сплутати з "просто bad").

## 4. Що навмисно НЕ тестуємо

- Точність метрик — відповідальність сервісу `parser` (тести там).
- Візуальна відповідність графіків (pixel-perfect) — крихко й не є критерієм оцінки;
  перевіряється лише факт рендеру canvas.
- Docker-образ — перевіряється окремо на етапі §5 плану (compose), не в цьому наборі.
