# Алгоритм оцінки якості пілотування (вердикт-шар)

Рішення: **if/else за наданими шаблонами, без LLM**  Цей документ описує сам
алгоритм так, щоб реальні пороги з good/bad-шаблонів підставлялись без зміни
коду — лише як конфіг.

## Вхід

JSON з детермінованими метриками, порахованими парсером (шар 1, без порогів і без вердикту):

```json
{
  "corrections_per_min": {"roll": 8.2, "pitch": 5.1, "yaw": 0.4},
  "mean_amplitude": {"roll": 0.18, "pitch": 0.11, "yaw": 0.02},
  "mean_jerk": {"roll": 0.9, "pitch": 0.5, "yaw": 0.05},
  "oscillation_time_pct": {"roll": 0.12, "pitch": 0.08, "yaw": 0.01},
  "reaction_latency_ms": 420
}
```

Значення нормалізовані відносно ходу стіка (0..1 від нейтралі до краю), крім
`corrections_per_min` (шт/хв) і `reaction_latency_ms` (мс) — конкретні одиниці узгодити при
отриманні реальних шаблонів.

## Конфіг порогів (з good/bad-шаблонів)

Пороги не хардкодяться в коді — окремий YAML/JSON, що завантажується сервісом:

```yaml
# thresholds.yaml — заповнюється зі шаблонів замовника, зараз placeholder-значення з демо-польоту
corrections_per_min:
  good_max: 6.0      # <= good_max -> "good"
  warn_max: 12.0      # <= warn_max -> "warning", вище -> "bad"
mean_amplitude:
  good_max: 0.15
  warn_max: 0.30
mean_jerk:
  good_max: 0.6
  warn_max: 1.2
oscillation_time_pct:
  good_max: 0.10
  warn_max: 0.25
reaction_latency_ms:
  good_max: 500
  warn_max: 1000
```

Поки офіційних шаблонів нема — числа тут орієнтовні, взяті з розвідки [[demo-flight-task.md]] (щоб
пайплайн можна було тестувати), і мають бути замінені на реальні одразу після отримання VPS-доступу.

## Алгоритм

1. Для кожної метрики (і, де є розбивка по осях — для кожної осі) порівняти значення з
   `good_max`/`warn_max`:
   - `value <= good_max` → `"good"`
   - `good_max < value <= warn_max` → `"warning"`
   - `value > warn_max` → `"bad"`
2. Загальний вердикт польоту = найгірша категорія серед усіх метрик/осей (worst-case, не
   середнє) — одна погана метрика не повинна "розчинятись" у хороших.
3. Короткий текстовий вердикт генерується шаблоном рядка на основі категорії й списку метрик, що
   в неї потрапили (наприклад: `"BAD: надмірна різкість по roll (mean_jerk=1.4, поріг 1.2)"`), без
   LLM — просто підстановка у f-string/template.

## Де виконується: сервер рахує метрики, клієнт рахує вердикт

Пороги (`good_max`/`warn_max`) — **налаштовувані на клієнті**, під час перегляду звіту, а не
захардкоджені в бекенді:

- Сервер (парсер) віддає в JSON польоту лише сирі метрики (незмінні, детерміновані) +
  дефолтні пороги з `thresholds.yaml` як стартові значення форми.
- Веб-сторінка польоту портує п.1-2 цього алгоритму на TS і виконує категоризацію **в браузері**.
  Пороги — інпути/слайдери в UI; зміна порогу миттєво перераховує вердикт без запиту на сервер,
  бо сама формула — чиста функція `(metrics, thresholds) -> verdict`.
- Це не порушує "метрики — детерміновано кодом": детермінованим і серверним лишається розрахунок
  самих метрик, а поріг інтерпретації — свідомо інтерактивний параметр перегляду, не метрика.
- Дефолтні пороги в UI = ті самі з `thresholds.yaml` (заповнити реальними зі шаблонів, коли
  прийдуть); глядач може підкрутити їх, щоб побачити, як зміна порогу впливає на вердикт —
  зручно і для ручної перевірки пайплайна, поки офіційних шаблонів ще нема.

## Вивід

Сервер віддає (без запеченого вердикту):

```json
{
  "metrics": { "...": "як у прикладі вище" },
  "default_thresholds": { "...": "вміст thresholds.yaml" }
}
```

Клієнт рахує й показує (локально, з поточних порогів у формі):

```json
{
  "verdict": "warning",
  "reasons": [
    {"metric": "oscillation_time_pct", "axis": "roll", "value": 0.12, "category": "warning"}
  ]
}
```

## Розширюваність

- Якщо реальні шаблони виявляться складнішими за прості пороги (наприклад, залежать від фази
  польоту чи комбінації метрик) — розширити алгоритм п.1 правилами `if metric_a and metric_b`
  замість табличних порогів, залишаючись у межах if/else (без LLM).
- Конфіг порогів версіонується окремо від коду (можна тримати кілька профілів — plane/quad, якщо
  знадобиться).
